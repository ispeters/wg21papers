# Abstract

The standard library offers two ways to declare an asynchronous function in one
place and define it in another, and each falls short. Returning a sender whose
type is specific to the function's implementation puts the structure of that
implementation in its declaration, so the implementation can't change without
changing the interface, and overrides of a virtual function can't differ in
structure. `std::execution::task` keeps the implementation out of the
declaration, but it's a coroutine type, and coroutines don't fit every domain.
This paper argues for a third way that avoids both shortcomings, sets out the
requirements a solution must meet, compares candidate designs against them, and
proposes `std::execution::function` as the best fit. Its main advantage is that
its only allocation is the activation frame that any such boundary requires.

This paper also proposes a minimal query, `std::execution::get_frame_allocator`,
so the caller's environment can choose how activation frames are allocated. The
query is inspired by Vinnie Falco *et al.*'s work in [@P4003R3] and [@P4172R1].
The rest of a frame-allocation design, ideally one shared by coroutines and
senders, is left to a later paper.

# Motivation

Declaring a function in one place and defining it in another is useful because
one declaration of a virtual function can have many definitions, and any
function's definition can change without its callers being recompiled. The
standard library offers two ways to separate an *asynchronous* function's
declaration from its definition, and each falls short. A running example shows
how, and what a third way looks like.

## A Key-Value Store

Consider an interface to a key-value store with a virtual `get`:

```{.cpp file="sync/kv_store.hpp" caption="kv_store.hpp"}
#include <optional>
#include <string>

struct kv_store {
  virtual ~kv_store() = default;
  virtual std::optional<std::string> get(std::string key) const = 0;
};
```

Two implementations of this interface appear throughout this paper:

```{.cpp file="sync/remote_store.hpp" caption="remote_store.hpp"}
#include "kv_store.hpp"

class remote_store final : public kv_store {
 public:
  // asks a remote server, so it waits on the network
  std::optional<std::string> get(std::string key) const override;
  // ...
};
```

```{.cpp file="sync/cache.hpp" caption="cache.hpp"}
#include "kv_store.hpp"

class cache final : public kv_store {
 public:
  explicit cache(kv_store const& backing);

  // answers hits immediately and forwards misses to the backing store
  std::optional<std::string> get(std::string key) const override;

 private:
  kv_store const* backing_;
  // ...
};
```

What should an asynchronous `get` return so that these declarations keep their
shape?

## Returning an Implementation-Specific Sender

One option for the return type of an asynchronous `get` is a sender whose type
is specific to the implementation. There are two ways to write one.

### Composing Standard Senders

The simpler way is to compose standard senders. The declaration can name the
composed type with `decltype` and leave the definition in a source file, with
the leaf logic in a named function object defined out of line. Here is
`remote_store` written that way, with a timer standing in for network latency
and a `std::map` standing in for the server's data. It stands alone for now;
the first consequence below explains why it can't override an asynchronous
`kv_store::get`.^[The examples use stdexec's
spellings so that they compile against the reference implementation: `STDEXEC`
names stdexec's implementation of `std::execution`, which is intended to conform
to the standard, and `exec` names its extensions, including the `function` this
paper proposes.]

```{.cpp file="composed/remote_store.hpp" caption="remote_store.hpp"}
#include <exec/timed_thread_scheduler.hpp>
#include <stdexec/execution.hpp>

#include <chrono>
#include <map>
#include <optional>
#include <string>
#include <utility>

namespace ex = STDEXEC;

// A function object that looks up a key. Ordinarily this would be a lambda in
// get's definition, but get_sender (below) must name its type, so it's a class
// whose call operator is defined in remote_store.cpp.
struct remote_lookup {
  // returns the value stored under key, or nullopt if there isn't one
  std::optional<std::string> operator()() const;

  // the data to search, which belongs to the remote_store that made this lookup
  std::map<std::string, std::string> const* data;
  std::string key;
};

class remote_store {
 public:
  remote_store(exec::timed_thread_scheduler latency,
               std::map<std::string, std::string> data);

  // The type get returns. It spells out how get is implemented: wait for a
  // timer, then call remote_lookup. Only types matter in decltype, so the
  // duration is a placeholder.
  using get_sender = decltype(
      exec::schedule_after(std::declval<exec::timed_thread_scheduler const&>(),
                           std::chrono::milliseconds{}) |
      ex::then(std::declval<remote_lookup>()));

  // The returned sender refers to this store's data, so the store must
  // outlive the lookup, but nothing in this declaration says so.
  get_sender get(std::string key) const;

 private:
  // stand-ins for a remote server's network latency and data
  exec::timed_thread_scheduler latency_;
  std::map<std::string, std::string> data_;
};
```

```{.cpp file="composed/remote_store.cpp" caption="remote_store.cpp"}
#include "remote_store.hpp"

#include <utility>

remote_store::remote_store(exec::timed_thread_scheduler latency,
                           std::map<std::string, std::string> data)
    : latency_(latency), data_(std::move(data)) {}

std::optional<std::string> remote_lookup::operator()() const {
  if (auto it = data->find(key); it != data->end()) {
    return it->second;
  }
  return std::nullopt;
}

remote_store::get_sender remote_store::get(std::string key) const {
  return exec::schedule_after(latency_, std::chrono::milliseconds{5}) |
         ex::then(remote_lookup{&data_, std::move(key)});
}
```

`remote_lookup::operator()` can change without touching the header, but the
`get_sender` type names every algorithm `get` uses, in order, so the structure
of `get`'s implementation is in its declaration. Leaking that structure into the
interface has three consequences:

1. **All overrides of a virtual function must have the same structure.**
   `kv_store` must choose one return type for `get`, and every override must
   return exactly that type, so with this approach, `kv_store` chooses one
   *structure* for every implementation, too. If it chooses
   `remote_store::get_sender`, every override must return a sender that waits
   for a timer before calling `remote_lookup`, so `cache::get`, which answers
   hits immediately and forwards misses to the backing store, can't override
   `kv_store::get`.

   Choosing a more flexible return type doesn't solve the problem. Replacing
   `remote_lookup` with `std::function` lets only the synchronous step at the
   leaf vary, so every implementation inherits `remote_store`'s timer, and on a
   miss, `cache::get` can wait for the backing store only by blocking. A type
   with optional steps, or a variant over several structures, permits only the
   structures `kv_store`'s author anticipates. Even if the author anticipates
   `cache`, no type is flexible enough; `cache::get` forwards misses to another
   `kv_store`, so the operation state of `kv_store::get`'s sender would have to
   contain another of its own type. Only erasing the
   sender's type breaks that recursion, so `kv_store` can't be written with
   implementation-specific senders.

2. **Changing the structure changes the interface.** Even when `get` isn't
   virtual, changing an implementation detail, like adding a timeout or retrying
   failures, changes `get_sender`, and with it the ABI, so every caller must be
   recompiled.

3. **The types are hard to write and to read.** The `get_sender` alias has to
   repeat the definition's expression closely enough to produce the same type,
   and diagnostics name the fully composed type.^[While this example was being
   written, a `decltype` that named the scheduler as an rvalue, where the
   definition used an lvalue, produced a different type in stdexec, because
   its `schedule_after` has a lambda in its type. That is a property of one
   implementation, not of the standard, but it illustrates how closely the
   declaration is tied to the definition.]

### Writing a Sender by Hand

The other way to write an implementation-specific sender is by hand. Its type
need not name any algorithms, and it can still reuse the standard ones if its
operation state connects a pipeline of standard senders to the receiver and
holds the pipeline's operation state as a member. However, since `connect` is a
template over the receiver, the type of the operation state it returns must be
defined in the header, along with the types of its members. The type of the
pipeline's operation state names the pipeline's type, so that member puts the
pipeline's type in the header, too. That is the approach of [Composing Standard
Senders] again, just one level deeper.

Keeping the pipeline out of the header takes more work. It starts like this:

```{.cpp file="handwritten/remote_store.hpp" caption="remote_store.hpp"}
#include <stdexec/execution.hpp>

#include <exception>
#include <optional>
#include <string>
#include <utility>

namespace ex = STDEXEC;

class remote_store;

// the caller's receiver, type-erased
class erased_receiver {
 public:
  using receiver_concept = ex::receiver_t;

  template <class Receiver>
  explicit erased_receiver(Receiver& rcvr) noexcept : rcvr_(&rcvr) {
    // ... and keep a pointer to a table of Receiver's completion functions
  }

  void set_value(std::optional<std::string> value) && noexcept;
  void set_error(std::exception_ptr error) && noexcept;
  void set_stopped() && noexcept;
  // ... and get_env, which must erase the receiver's environment, too

 private:
  void* rcvr_;
  // ... the pointer to that table
};

// the operation state's non-template part, whose member functions are defined
// in remote_store.cpp
class get_operation_base {
 public:
  get_operation_base(remote_store const& store, std::string key,
                     erased_receiver rcvr);
  get_operation_base(get_operation_base&&) = delete;
  void start() & noexcept;

 private:
  // the pipeline's operation state must live here, as one of:
  //  - a member, whose type names the pipeline,
  //  - a fixed-size buffer, whose size becomes part of the ABI, or
  //  - an allocation, which needs a policy for where the memory comes from
};

template <class Receiver>
struct receiver_holder {
  Receiver rcvr;
};

// receiver_holder comes first so the receiver exists before
// get_operation_base's constructor can use it
template <class Receiver>
class get_operation : receiver_holder<Receiver>, public get_operation_base {
 public:
  using operation_state_concept = ex::operation_state_t;

  get_operation(remote_store const& store, std::string key, Receiver rcvr)
      : receiver_holder<Receiver>{std::move(rcvr)},
        get_operation_base(store, std::move(key),
                           erased_receiver(this->rcvr)) {}
};

struct get_sender {
  using sender_concept = ex::sender_t;

  template <class Self, class... Env>
  static consteval auto get_completion_signatures() noexcept {
    return ex::completion_signatures<
        ex::set_value_t(std::optional<std::string>),
        ex::set_error_t(std::exception_ptr), ex::set_stopped_t()>();
  }

  template <class Receiver>
  get_operation<Receiver> connect(Receiver rcvr) && {
    return {*store, std::move(key), std::move(rcvr)};
  }

  remote_store const* store;
  std::string key;
};

class remote_store {
 public:
  get_sender get(std::string key) const;
  // ...
};
```

`get_operation_base`'s comment lists three places the pipeline's operation state
could live. A member is the one just ruled out. A buffer limits the size of
every implementation and can't grow without changing the ABI, so in general the
pipeline's operation state must be allocated, which needs a policy for where the
memory comes from. If the policy comes from the receiver's environment,
`get_operation_base`'s constructor needs the receiver, which is why the receiver
lives in `receiver_holder`, a base class constructed first. For the abstract
`kv_store::get` to return a hand-written sender, every override must return the
same type, so `get_operation_base` must also dispatch to each implementation's
pipeline. Allocating the pipeline's operation state, erasing the receiver and
its environment, and dispatching to each implementation is type erasure, written
by hand for *one* signature. [Designs Considered] completes that type erasure,
and the result is a specialization of the type this paper proposes.

## Returning `task`

Another option is to return `std::execution::task`, a sender that is also a
coroutine type:

```{.cpp file="coro/kv_store.hpp" caption="kv_store.hpp"}
#include <stdexec/execution.hpp>

#include <optional>
#include <string>

namespace ex = STDEXEC;

struct kv_store {
  virtual ~kv_store() = default;
  virtual ex::task<std::optional<std::string>> get(std::string key) const = 0;
};
```

`remote_store` declares `get` with the interface's return type and defines it as
a coroutine:

```{.cpp file="coro/remote_store.hpp" caption="remote_store.hpp"}
#include "kv_store.hpp"

#include <exec/timed_thread_scheduler.hpp>

#include <map>

class remote_store final : public kv_store {
 public:
  remote_store(exec::timed_thread_scheduler latency,
               std::map<std::string, std::string> data);

  ex::task<std::optional<std::string>> get(std::string key) const override;

 private:
  exec::timed_thread_scheduler latency_;
  std::map<std::string, std::string> data_;
};
```

```{.cpp file="coro/remote_store.cpp" caption="remote_store.cpp"}
#include "remote_store.hpp"

#include <chrono>
#include <utility>

remote_store::remote_store(exec::timed_thread_scheduler latency,
                           std::map<std::string, std::string> data)
    : latency_(latency), data_(std::move(data)) {}

ex::task<std::optional<std::string>> remote_store::get(std::string key) const {
  co_await exec::schedule_after(latency_, std::chrono::milliseconds{5});
  if (auto it = data_.find(key); it != data_.end()) {
    co_return it->second;
  }
  co_return std::nullopt;
}
```

`task` keeps the implementation out of the declaration. `remote_store` and
`cache` can both override this `get`, and either body can change without
changing the interface. [Designs Considered] returns to `task`'s costs, but the
shortfall that matters here is simpler: `task` is a coroutine type, and
coroutines don't fit every domain. GPU device code is the clearest
example. NVIDIA's CUDA documentation lists coroutines among the C++20 features
that NVCC doesn't support in device
code^[[https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/cpp-language-support.html](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/cpp-language-support.html),
table "C++20 Language Features Supported by NVCC for device code".], and AMD's
HIP documentation says that coroutines aren't available in device
code^[[https://rocm.docs.amd.com/projects/HIP/en/develop/how-to/kernel_language_cpp_support.html](https://rocm.docs.amd.com/projects/HIP/en/develop/how-to/kernel_language_cpp_support.html).].

## A Third Way

A third option, which this paper proposes, is a sender type that lets the
asynchronous `get` be declared much like the synchronous one:

```{.cpp file="fn/kv_store.hpp" caption="kv_store.hpp"}
#include "async_fn.hpp"

#include <optional>
#include <string>

struct kv_store {
  virtual ~kv_store() = default;
  virtual async_fn<std::optional<std::string>(std::string) const &>
  get(std::string key) const = 0;
};
```

Read the template argument as the signature it parallels. Calling `get(key)`
doesn't look anything up; it returns a sender that represents the lookup, with
`key` already supplied. The lookup begins when the sender is started, and on
success completes with the `std::optional<std::string>` the synchronous `get`
would have returned. The `const &` says that the sender borrows the store, which
must outlive the operation, a dependence that `get_sender`'s declaration in
[Composing Standard Senders] left unstated (see [Interface Discussion]).

`async_fn` is local to this paper; it is not proposed (see [Future
Directions]). It is an alias for a specialization of the type this paper
proposes, `std::execution::function`:

```{.cpp file="fn/async_fn.hpp" caption="async_fn.hpp"}
#include <exec/function.hpp>
#include <stdexec/execution.hpp>

#include <exception>

namespace ex = STDEXEC;

template <class Sig>
struct async_fn_for;

template <class R, class... Args>
struct async_fn_for<R(Args...) const &> {
  using type = exec::function<
      ex::sender_tag(Args...) const &,
      ex::completion_signatures<ex::set_value_t(R),
                                ex::set_error_t(std::exception_ptr),
                                ex::set_stopped_t()>>;
};

template <class Sig>
using async_fn = typename async_fn_for<Sig>::type;
```

As with `task`, `remote_store`'s declaration repeats the interface's, and the
structure of its implementation stays in its source file:

```{.cpp file="fn/remote_store.hpp" caption="remote_store.hpp"}
#include "kv_store.hpp"

#include <exec/timed_thread_scheduler.hpp>

#include <map>

class remote_store final : public kv_store {
 public:
  remote_store(exec::timed_thread_scheduler latency,
               std::map<std::string, std::string> data);

  async_fn<std::optional<std::string>(std::string) const &>
  get(std::string key) const override;

 private:
  exec::timed_thread_scheduler latency_;
  std::map<std::string, std::string> data_;
};
```

```{.cpp file="fn/remote_store.cpp" caption="remote_store.cpp"}
#include "remote_store.hpp"

#include <chrono>
#include <utility>

remote_store::remote_store(exec::timed_thread_scheduler latency,
                           std::map<std::string, std::string> data)
    : latency_(latency), data_(std::move(data)) {}

async_fn<std::optional<std::string>(std::string) const &>
remote_store::get(std::string key) const {
  return async_fn<std::optional<std::string>(std::string) const &>(
      *this, std::move(key), [](remote_store const& self, std::string key) {
        return exec::schedule_after(self.latency_,
                                    std::chrono::milliseconds{5}) |
               ex::then([data = &self.data_, key = std::move(key)] {
                 std::optional<std::string> value;
                 if (auto it = data->find(key); it != data->end()) {
                   value = it->second;
                 }
                 return value;
               });
      });
}
```

`cache`'s declaration differs from the synchronous one in [A Key-Value Store]
only in `get`'s return type; [Designs Considered] implements it with each
candidate design:

```{.cpp file="fn/cache.hpp" caption="cache.hpp"}
#include "cache_entries.hpp"
#include "kv_store.hpp"

class cache final : public kv_store {
 public:
  explicit cache(kv_store const& backing);

  // answers hits immediately and forwards misses to the backing store
  async_fn<std::optional<std::string>(std::string) const &>
  get(std::string key) const override;

 private:
  kv_store const* backing_;
  mutable cache_entries entries_;
};
```

Both implementations override `get` as they did synchronously, so the
declarations keep their shape. Unlike `task`, `async_fn` doesn't require the
body to be a coroutine; `remote_store::get` returns a sender expression instead.
[Requirements] states what a solution must provide, and the sections after it
measure each candidate, this one included, against those requirements.

# Requirements

A synchronous function already has most of what [Motivation] asks of an
asynchronous one, so most of these requirements ask a solution to keep a
property that synchronous functions have. Each states a need that exists
whatever design meets it. All but the eighth are met or not; ergonomics is a
matter of degree.

1. **Separation of interface and implementation.** An asynchronous function's
   declaration must not depend on its implementation, so that the definition
   can change without changing the interface, and overrides of a virtual
   function can be implemented differently. [Returning an
   Implementation-Specific Sender] shows that a sender whose type is specific
   to the implementation fails both.

2. **Composable with other senders.** Calling the function must produce a
   sender, so that the standard algorithms, and other functions declared the
   same way, can consume the result like any other sender. A boundary that left
   the sender ecosystem would solve one problem by creating another.

3. **Fully general.** Any asynchronous function that a sender can represent
   must be declarable, with any combination of completion signatures and any
   environment queries. Real interfaces need this. nvexec's stream senders, for
   example, report CUDA failures as `set_error_t(cudaError_t)`, so a design that
   fixes the error type couldn't declare them.

4. **Broadly applicable.** The solution must not depend on language features
   that some of the domains senders serve lack. GPU device code, where
   coroutines aren't available ([Returning `task`]), is the clearest example.

5. **Allocation like a stack frame.** A synchronous call allocates only its
   stack frame, from memory the calling thread already owns, and frees it before
   the call returns. An asynchronous operation can outlive the call that started
   it, so its frame must generally be allocated dynamically, but the rest of
   that model should still hold.

   a. **No allocation beyond the activation frame.** The only memory an
      operation allocates is the frame that holds its state. Calling the
      function and moving the sender it returns allocate nothing that a
      synchronous call wouldn't.
   b. **The caller's environment chooses the frame allocator.** A synchronous
      function doesn't choose the stack it runs on. An allocator parameter at
      every call site, or state passed out of band, would make every signature
      in a call tree carry the choice; [@P4007R3] (section 3) describes that
      cost for `task`'s `allocator_arg`.
   c. **Frame lifetimes nest along sequential paths.** Along any sequence of
      operations, a frame allocated while another is live is freed first, so a
      frame allocator can be as simple as a stack. [@P4172R1] (section 6.3)
      relies on the same property of coroutine frames ("sizes repeat, lifetimes
      nest") for its recycling allocator. Frames on parallel branches coexist
      rather than nest.

6. **A precise failure contract.** It must be possible to declare and use such
   functions without exceptions, and the type must be able to say that the work
   done before the operation starts doesn't throw, as `noexcept` does for a
   synchronous function. Asynchronous failure already has a precise contract in
   the completion signatures. Some domains build without exceptions; stdexec's
   own continuous integration includes builds with
   `-fno-exceptions`.^[[https://github.com/NVIDIA/stdexec/blob/main/.github/workflows/ci.cpu.yml](https://github.com/NVIDIA/stdexec/blob/main/.github/workflows/ci.cpu.yml)]

7. **Borrowed state visible in the interface.** If an operation depends on an
   object outliving it, the declaration must say so, as a member function's
   declaration says that the call uses `*this`. In [Composing Standard
   Senders], `get` returns a sender that refers to the store, and its
   declaration can say so only in a comment.

8. **Ergonomics.** Interface boundaries occur at every layer of a program, so
   their costs are paid often.

   a. **Declaring an interface** should be about as easy as declaring the
      synchronous function it parallels.
   b. **Writing an implementation** should be about as easy as writing the work
      itself. Coroutines set the bar here, as `remote_store::get` in [Returning
      `task`] shows.

9. **Standard vocabulary.** Libraries must be able to use the solution in their
   interfaces without agreeing on anything beyond the standard, and without
   writing boilerplate for each interface. Two libraries that each wrote their
   own would have incompatible types.

# Designs Considered

Each design below implements `cache`, the decorator from [A Third Way] that
answers hits immediately and forwards misses to its backing store.
[Motivation] already showed `remote_store` with `task` and with `function`, but
`cache` is the harder case, because its two paths complete differently and one
of them calls through the interface it implements. Each `cache.hpp` differs
from [A Third Way]'s only in `get`'s return type, so only that one is shown, and
its `cache_entries` member, also not shown, is a map guarded by a mutex. The
first design writes `cache::get` as a coroutine; the other three write it as
one sender expression and differ only in how they erase its type. This section
describes how each design works and what it costs; [Comparison] measures them
against [Requirements].

## `task`

With `kv_store::get` declared as in [Returning `task`], `cache::get` is a
coroutine:

```{.cpp file="coro/cache.cpp" caption="cache.cpp"}
#include "cache.hpp"

#include <utility>

cache::cache(kv_store const& backing) : backing_(&backing) {}

ex::task<std::optional<std::string>> cache::get(std::string key) const {
  if (auto value = entries_.find(key)) {
    co_return value;
  }
  auto value = co_await backing_->get(key);
  if (value) {
    entries_.insert(std::move(key), *value);
  }
  co_return value;
}
```

It reads like the synchronous `cache::get` it replaces: a hit returns early,
and a miss waits for the backing store where the synchronous version would have
called it. None of the other designs makes an implementation this easy to
write.

Calling `get` allocates the coroutine's frame, which holds the parameters, the
locals that live across a suspension point, and the state of whatever the body
is awaiting, so the frame is the only allocation a call needs. However, it is
allocated when `get` is called, before the returned `task` is connected to a
receiver, so the caller's environment can't choose how. A caller that wants a
different frame allocator must pass one as an `allocator_arg` argument, so
`kv_store::get`'s declaration needs a parameter for it, which every override
must accept and every caller must supply, though it has nothing to do with
looking up a key. [@P4007R3] (section 3) explains why letting the environment
choose instead would take a change to the language.

[@P4088R1] and [@P4100R1] argue that coroutines are the right tool for
type-erased asynchronous boundaries in I/O libraries, because a coroutine's
frame erases its type, and the allocation that a boundary needs anyway pays for
the erasure. This paper agrees that a boundary costs one frame. Both papers also
leave GPU and other heterogeneous work to senders, and that is where
[Returning `task`] showed that coroutines aren't available.

## Erasing a Sender Expression

Without a coroutine, `cache::get`'s body is a sender expression. This one is
written once for the three designs that follow, as a template over the backing
store's type, because each design's `kv_store` is a different class; a real
cache would name its backing type.

```{.cpp file="cached_lookup.hpp" caption="cached_lookup.hpp"}
#include "cache_entries.hpp"

#include <exec/variant_sender.hpp>
#include <stdexec/execution.hpp>

#include <optional>
#include <string>
#include <utility>

namespace ex = STDEXEC;

// looks key up in entries, and on a miss in backing, caching what it finds
template <class Store>
auto cached_lookup(Store const& backing, cache_entries& entries,
                   std::string key) {
  return ex::just(std::move(key)) |
         ex::let_value([&backing, &entries](std::string const& key) {
           auto miss = [&] {
             return backing.get(key) |
                    ex::then([&entries, &key](std::optional<std::string> value) {
                      if (value) {
                        entries.insert(key, *value);
                      }
                      return value;
                    });
           };
           // a hit and a miss are different senders, so return a variant
           using lookup = exec::variant_sender<
               decltype(ex::just(std::optional<std::string>())),
               decltype(miss())>;
           if (auto value = entries.find(key)) {
             return lookup(ex::just(std::move(value)));
           }
           return lookup(miss());
         });
}
```

`let_value` runs its continuation when `just` completes, so the lookup happens
after the operation starts, and a lookup started later sees entries inserted in
the meantime. The continuation must return one sender type, so the hit and the
miss, which are different senders, go in a variant sender. stdexec provides
`exec::variant_sender`, and [@P4329R0] proposes
`std::execution::variant_sender`. Naming the miss's type also takes a
`decltype`. This is the cost of writing an implementation as a sender
expression rather than a coroutine, and the `task` version pays none of it.

### `any_sender`

stdexec's `exec::any_sender`, like libunifex's `unifex::any_sender_of` before
it, erases the type of any sender that supports the completion signatures and
queries named in its type:

```{.cpp file="any/kv_store.hpp" caption="kv_store.hpp"}
#include <exec/any_sender_of.hpp>
#include <stdexec/execution.hpp>

#include <exception>
#include <optional>
#include <string>

namespace ex = STDEXEC;

using any_lookup = exec::any_sender<exec::any_receiver<
    ex::completion_signatures<ex::set_value_t(std::optional<std::string>),
                              ex::set_error_t(std::exception_ptr),
                              ex::set_stopped_t()>>>;

struct kv_store {
  virtual ~kv_store() = default;
  virtual any_lookup get(std::string key) const = 0;
};
```

`cache::get` returns the sender expression, and `any_lookup` stores it:

```{.cpp file="any/cache.cpp" caption="cache.cpp"}
#include "cache.hpp"
#include "cached_lookup.hpp"

#include <utility>

cache::cache(kv_store const& backing) : backing_(&backing) {}

any_lookup cache::get(std::string key) const {
  return cached_lookup(*backing_, entries_, std::move(key));
}
```

Constructing an `any_sender` stores the sender, which means allocating unless
the sender fits a small buffer (three pointers in stdexec). Connecting it
connects the stored sender to a receiver that erases the caller's; the
resulting operation state's type depends on the stored sender, so it's
allocated too, and `connect` returns an operation state of fixed size that owns
it, whose `start` is an indirect call. A call can therefore cost two
allocations. The first happens before the caller's environment is known, so
the environment can't choose its allocator. In principle, an `any_sender` could
accept an allocator for that storage when it's constructed, as `task` accepts
an `allocator_arg` argument, but with the same cost: `kv_store::get`'s
declaration would need a parameter for it, unrelated to looking up a key.

Because the erased receiver's type is fixed by the `any_sender`'s type, the
stored sender's operation-state type is known as soon as the sender is. A
variant of `any_sender` could therefore allocate once, at construction, enough
storage for both the sender and the operation state it will become. That
variant has `task`'s profile: one allocation, made before the caller's
environment is available.

### Writing It Yourself

[Writing a Sender by Hand] stopped where the pipeline's operation state needed a
home. Completing that sketch for `kv_store` starts with making 3.2.2's
`get_sender` the return type of the abstract `get`:

```{.cpp file="diy/kv_store.hpp" caption="kv_store.hpp"}
#include "get_sender.hpp"

struct kv_store {
  virtual ~kv_store() = default;
  virtual get_sender get(std::string key) const = 0;
};
```

and then finishing the type erasure it began. Here is a minimal version, as an
expert might write it in C++26:

```{.cpp file="diy/get_sender.hpp" caption="get_sender.hpp"}
#include <stdexec/execution.hpp>

#include <exception>
#include <memory>
#include <memory_resource>
#include <optional>
#include <string>
#include <utility>

namespace ex = STDEXEC;

// the caller's environment, type-erased: its stop token and allocator,
// converted to fixed types
struct erased_env {
  ex::inplace_stop_token stop_token;
  std::pmr::polymorphic_allocator<> allocator;

  auto query(ex::get_stop_token_t) const noexcept { return stop_token; }
  auto query(ex::get_allocator_t) const noexcept { return allocator; }
};

// a receiver that forwards completions to a Target it doesn't know the type of
class erased_receiver {
 public:
  using receiver_concept = ex::receiver_t;

  template <class Target>
  erased_receiver(Target& target, erased_env env) noexcept
      : target_(&target), vtable_(&vtable_for<Target>), env_(env) {}

  void set_value(std::optional<std::string> value) && noexcept {
    vtable_->set_value(target_, std::move(value));
  }
  void set_error(std::exception_ptr error) && noexcept {
    vtable_->set_error(target_, std::move(error));
  }
  void set_stopped() && noexcept { vtable_->set_stopped(target_); }
  erased_env get_env() const noexcept { return env_; }

 private:
  struct vtable {
    void (*set_value)(void*, std::optional<std::string>) noexcept;
    void (*set_error)(void*, std::exception_ptr) noexcept;
    void (*set_stopped)(void*) noexcept;
  };

  template <class Target>
  static constexpr vtable vtable_for{
      [](void* target, std::optional<std::string> value) noexcept {
        static_cast<Target*>(target)->set_value(std::move(value));
      },
      [](void* target, std::exception_ptr error) noexcept {
        static_cast<Target*>(target)->set_error(std::move(error));
      },
      [](void* target) noexcept { static_cast<Target*>(target)->set_stopped(); }};

  void* target_;
  vtable const* vtable_;
  erased_env env_;
};

// an implementation's pipeline, connected to an erased_receiver and allocated
class pipeline {
 public:
  virtual void start() noexcept = 0;
  virtual void destroy(std::pmr::polymorphic_allocator<> alloc) noexcept = 0;

 protected:
  ~pipeline() = default;
};

template <class Sender>
class pipeline_for final : public pipeline {
 public:
  pipeline_for(Sender sndr, erased_receiver rcvr)
      : op_(ex::connect(std::move(sndr), std::move(rcvr))) {}

  void start() noexcept override { ex::start(op_); }
  void destroy(std::pmr::polymorphic_allocator<> alloc) noexcept override {
    alloc.delete_object(this);
  }

 private:
  ex::connect_result_t<Sender, erased_receiver> op_;
};

// makes, connects and allocates one implementation's pipeline
using connect_fn = pipeline* (*)(void const* store, std::string key,
                                 erased_receiver rcvr,
                                 std::pmr::polymorphic_allocator<> alloc);

// the allocation policy: the caller's allocator if it's polymorphic,
// otherwise the default memory resource
template <class Env>
std::pmr::polymorphic_allocator<> allocator_of(Env const& env) noexcept {
  if constexpr (requires {
                  std::pmr::polymorphic_allocator<>(ex::get_allocator(env));
                }) {
    return std::pmr::polymorphic_allocator<>(ex::get_allocator(env));
  } else {
    return {};
  }
}

// the operation state's non-template part
class get_operation_base {
 public:
  get_operation_base(connect_fn connect, void const* store, std::string key,
                     erased_receiver rcvr, std::pmr::polymorphic_allocator<> alloc)
      : alloc_(alloc),
        pipeline_(connect(store, std::move(key), std::move(rcvr), alloc)) {}
  get_operation_base(get_operation_base&&) = delete;
  ~get_operation_base() { pipeline_->destroy(alloc_); }
  void start() & noexcept { pipeline_->start(); }

 private:
  std::pmr::polymorphic_allocator<> alloc_;
  pipeline* pipeline_;
};

// The caller's receiver, and a callback that forwards stop requests from the
// caller's stop token to the pipeline's. The callback must be destroyed before
// the receiver completes, so the pipeline completes here, not to the receiver.
// The callback lives exactly from start to completion, so its lifetime is
// managed by hand rather than with a flag.
template <class Receiver>
class receiver_holder {
 public:
  void set_value(std::optional<std::string> value) noexcept {
    std::destroy_at(&callback_);
    ex::set_value(std::move(rcvr_), std::move(value));
  }
  void set_error(std::exception_ptr error) noexcept {
    std::destroy_at(&callback_);
    ex::set_error(std::move(rcvr_), std::move(error));
  }
  void set_stopped() noexcept {
    std::destroy_at(&callback_);
    ex::set_stopped(std::move(rcvr_));
  }

 protected:
  explicit receiver_holder(Receiver rcvr) : rcvr_(std::move(rcvr)) {}
  ~receiver_holder() {}

  void forward_stop_requests() noexcept {
    std::construct_at(&callback_, ex::get_stop_token(ex::get_env(rcvr_)),
                      forward_stop{&stop_source_});
  }

  Receiver rcvr_;
  ex::inplace_stop_source stop_source_;

 private:
  struct forward_stop {
    ex::inplace_stop_source* source;
    void operator()() const noexcept { source->request_stop(); }
  };
  using token = ex::stop_token_of_t<ex::env_of_t<Receiver>>;

  union {
    ex::stop_callback_for_t<token, forward_stop> callback_;
  };
};

// receiver_holder comes first so the receiver exists before
// get_operation_base's constructor connects the pipeline
template <class Receiver>
class get_operation : receiver_holder<Receiver>, public get_operation_base {
 public:
  using operation_state_concept = ex::operation_state_t;

  get_operation(connect_fn connect, void const* store, std::string key,
                Receiver rcvr)
      : receiver_holder<Receiver>(std::move(rcvr)),
        get_operation_base(
            connect, store, std::move(key),
            erased_receiver(static_cast<receiver_holder<Receiver>&>(*this),
                            {this->stop_source_.get_token(), alloc()}),
            alloc()) {}

  void start() & noexcept {
    this->forward_stop_requests();
    get_operation_base::start();
  }

 private:
  std::pmr::polymorphic_allocator<> alloc() const noexcept {
    return allocator_of(ex::get_env(this->rcvr_));
  }
};

class get_sender {
  using signatures =
      ex::completion_signatures<ex::set_value_t(std::optional<std::string>),
                                ex::set_error_t(std::exception_ptr),
                                ex::set_stopped_t()>;

 public:
  using sender_concept = ex::sender_t;

  template <class Self, class... Env>
  static consteval auto get_completion_signatures() noexcept {
    return signatures();
  }

  // a lookup of key in store, whose pipeline Factory makes; Factory must be
  // stateless, so only its type is kept
  template <class Store, class Factory>
  get_sender(Store const& store, std::string key, Factory)
      : store_(&store), key_(std::move(key)),
        connect_(&connect_with<Store, Factory>) {}

  template <ex::receiver_of<signatures> Receiver>
  get_operation<Receiver> connect(Receiver rcvr) && {
    return {connect_, store_, std::move(key_), std::move(rcvr)};
  }

 private:
  template <class Store, class Factory>
  static pipeline* connect_with(void const* store, std::string key,
                                erased_receiver rcvr,
                                std::pmr::polymorphic_allocator<> alloc) {
    auto sndr = Factory()(*static_cast<Store const*>(store), std::move(key));
    return alloc.new_object<pipeline_for<decltype(sndr)>>(std::move(sndr),
                                                          std::move(rcvr));
  }

  void const* store_;
  std::string key_;
  connect_fn connect_;
};
```

Each piece embodies a decision that every author of such a type must make:

| Piece | Lines | What it decides |
|:------|------:|:----------------|
| `erased_env` | 6 | Which of the caller's queries an implementation can see: here, only the stop token and the allocator, converted to fixed types |
| `erased_receiver` | 33 | How completions reach the caller: a pointer to the operation state and a table of its three completion functions |
| `pipeline`, `pipeline_for` | 19 | How an implementation's operation state is erased: a virtual `start` and `destroy` |
| `connect_fn`, `allocator_of` | 13 | Where the operation state's memory comes from: the caller's allocator if it's a `std::pmr::polymorphic_allocator`, otherwise the default memory resource |
| `get_operation_base` | 14 | When that memory is allocated (at `connect`) and freed (when the operation state is destroyed) |
| `receiver_holder`, `get_operation` | 54 | How the caller's stop requests reach the implementation: a callback that forwards them to an `inplace_stop_source`, destroyed before the caller's receiver completes |
| `get_sender` | 32 | How each implementation supplies its pipeline: a stateless factory, called with the store and the key at `connect` |

C++26 has no query for a frame allocator, so `allocator_of` uses
`get_allocator`. The type is minimal in other ways, too: it can't say that
`connect` doesn't throw, and it allocates every operation state, however small.

With `get_sender` complete, `cache::get` passes it a factory that returns the
sender expression:

```{.cpp file="diy/cache.cpp" caption="cache.cpp"}
#include "cache.hpp"
#include "cached_lookup.hpp"

#include <utility>

cache::cache(kv_store const& backing) : backing_(&backing) {}

get_sender cache::get(std::string key) const {
  return get_sender(*this, std::move(key),
                    [](cache const& self, std::string key) {
                      return cached_lookup(*self.backing_, self.entries_,
                                           std::move(key));
                    });
}
```

`get_sender`'s constructor takes the same arguments as `async_fn`'s in
[`function`], and this `cache::get` differs from that one only in its return
type. Completing the type erasure begun in [Writing a Sender by Hand] has
produced `function`, specialized to `get`'s signature. The 171 lines serve that
one signature, though. An interface with a different signature needs them
again, specialized to its own completions and queries, and two libraries that
each write their own get two different types, even for the same signature, so
neither library's interfaces can return the other's senders.

### `function`

With `kv_store::get` declared through `async_fn` as in [A Third Way],
`cache::get` returns a `function` built from the arguments and the same factory:

```{.cpp file="fn/cache.cpp" caption="cache.cpp"}
#include "cache.hpp"
#include "cached_lookup.hpp"

#include <utility>

cache::cache(kv_store const& backing) : backing_(&backing) {}

async_fn<std::optional<std::string>(std::string) const &>
cache::get(std::string key) const {
  return async_fn<std::optional<std::string>(std::string) const &>(
      *this, std::move(key), [](cache const& self, std::string key) {
        return cached_lookup(*self.backing_, self.entries_, std::move(key));
      });
}
```

Calling `get` doesn't look anything up. It returns a pending call: `*this` and
`key`, stored in the `function` along with the factory, a captureless lambda
whose type the constructor erases. Connecting the `function` calls the factory
with the stored arguments, connects the sender it returns to a receiver that
erases the caller's, and puts the resulting operation state in a frame
allocated through the frame allocator that the caller's environment provides
([Frame Allocation]). As with `any_sender`, `connect` returns an operation state
of fixed size that owns that frame, and `start` is an indirect call. Since
constructing a `function` only stores its arguments, the frame is the only
allocation, and it is made once the caller's environment is known.

The factory returns the sender expression that the `any_sender` version
stores; the two differ in when that sender is made and where its operation
state lives.

# Comparison

## Feature Comparison

[Designs Considered] implemented `cache` four ways. Each gives `get` one fixed
return type and keeps whatever varies between implementations behind that type,
reached only through indirect calls. The caller can't see what varies, so to the
caller it is storage of unknown size. The designs differ in when that storage is
first needed, which decides what each type must name and when it allocates:

+--------------------------+-----------------------+-----------------------+-----------------------+---------------------------+
| Property                 | `task`                | `any_sender`          | Writing It Yourself   | `function`                |
+:=========================+:======================+:======================+:======================+:==========================+
| When is storage of       | Calling `get`: the    | Calling `get`: the    | Connecting: the       | Connecting: the           |
| unknown size first       | coroutine frame       | sender                | operation state       | operation state           |
| needed?                  |                       |                       |                       |                           |
+--------------------------+-----------------------+-----------------------+-----------------------+---------------------------+
| What does the type name? | The value type\       | Completions\          | Whatever its author   | Completions\              |
|                          | Error types           | Queries               | chose                 | Queries and attributes\   |
|                          |                       |                       |                       | Parameter types\          |
|                          |                       |                       |                       | Whether it borrows an     |
|                          |                       |                       |                       | object                    |
+--------------------------+-----------------------+-----------------------+-----------------------+---------------------------+
| What does calling `get`  | The coroutine frame,  | The sender            | The arguments         | The arguments             |
| store?                   | holding the arguments |                       |                       |                           |
+--------------------------+-----------------------+-----------------------+-----------------------+---------------------------+
| Does calling `get`       | Yes                   | Unless the sender     | No                    | No                        |
| allocate?                |                       | fits a small buffer   |                       |                           |
+--------------------------+-----------------------+-----------------------+-----------------------+---------------------------+
| Does `connect` allocate? | No                    | Yes                   | Yes                   | At most once              |
+--------------------------+-----------------------+-----------------------+-----------------------+---------------------------+

The hand-written `get_sender` and `function` erase a factory rather than a
sender, so calling `get` stores only its arguments and allocates nothing. The
price is that `function` erases less than `any_sender`. Its type names the
parameter types, and its layout depends on them, because it stores the
arguments in place. An `any_sender`'s type depends only on its completions and
queries. Code that stores or forwards the senders an interface returns, without
calling the interface, therefore depends on the interface's parameter types if
the interface returns a `function`, and not if it returns an `any_sender`. Where
those types aren't stable, `any_sender` makes ABI stability easier. Callers of
`get` depend on its parameter types with either design, as callers of a
synchronous function do.

## Requirements Comparison

Measured against [Requirements], the four designs compare as follows. Each
mark judges what a design can do, not what today's implementations of it do;
meeting every requirement can take a lot of work, as the pieces that [Writing
It Yourself] needed showed. A design is the one [Designs Considered] describes,
extended in any way that doesn't change its nature; a variant that trades one
requirement for another, such as the merged `any_sender`, is discussed in the
text rather than marked. `task` is already standard, so a change counts for it
only if WG21 might make that change to a type it has shipped.

| Requirement | `task` | `any_sender` | Writing It Yourself | `function` |
| :---- | :----: | :----: | :----: | :----: |
| 1. Separation of interface and implementation | ✅ | ✅ | ✅ | ✅ |
| 2. Composable with other senders | ✅ | ✅ | ✅ | ✅ |
| 3. Fully general | ❌ | ✅ | ✅ | ✅ |
| 4. Broadly applicable | ❌ | ✅ | ✅ | ✅ |
| 5a. No allocation beyond the activation frame | ✅ | ❌ | ✅ | ✅ |
| 5b. The caller's environment chooses the frame allocator | ❌ | ✅ | ✅ | ✅ |
| 5c. Frame lifetimes nest along sequential paths | ❌ | ✅ | ✅ | ✅ |
| 6. A precise failure contract | ✅ | ✅ | ✅ | ✅ |
| 7. Borrowed state visible in the interface | ❌ | ❌ | ✅ | ✅ |
| 8a. Declaring an interface | ✅ | 🟡 | 🟡 | 🟡 |
| 8b. Writing an implementation | ✅ | 🟡 | 🟡 | 🟡 |
| 9. Standard vocabulary | ✅ | ✅ | ❌ | ✅ |

The rows that need explaining:

- **3. Fully general.** `task` has one value completion, and it always has
  `set_stopped_t()` ([task.members]{.sref}), so it can't declare a function
  that completes with either of two value types. The other designs take any
  completion signatures.
- **4. Broadly applicable.** `task` is a coroutine type, and coroutines aren't
  available in device code ([Returning `task`]). The other designs use no
  language feature that device code lacks, though `function`'s reference
  implementation hasn't yet been shown running there. Device code does charge
  for separating an interface from its implementation, whatever the design.
  Calling across translation units requires relocatable device code, which
  gives up optimization across files unless device link-time optimization
  recovers it ([@NVIDIA-LTO]). Host and device code have separate vtables, so
  an object with virtual functions must be constructed on the device to be
  called there, and virtual calls in parallel code are generally discouraged
  ([@Kokkos-virtual]). The other designs pay those costs; `task` can't be used
  in device code at all.
- **5a. No allocation beyond the activation frame.** `any_sender` allocates
  when `get` is called, to store the sender, as well as allocating its frame at
  `connect`. The merged variant in [`any_sender`] allocates only once, but
  trades 5a for 5b and 5c.
- **5b. The caller's environment chooses the frame allocator.** `task`
  allocates its frame when the coroutine is called, before any environment
  exists, so choosing a frame allocator takes an `allocator_arg` parameter in
  every signature ([`task`]). `any_sender`'s frame, the operation state, is
  allocated at `connect`, so the caller's frame allocator can provide it; its
  allocation in `get` is 5a's failure, not this one's. The merged variant
  allocates its frame in `get`, as `task` does, so it fails 5b and 5c.
- **5c. Frame lifetimes nest along sequential paths.** `task`'s frame is
  allocated when the coroutine is called, so the code that calls the
  coroutines decides the order of their frames, not the algorithm that runs
  them. The usual `co_await f()` nests, but nothing guarantees it: a coroutine
  that makes two `task`s and then awaits them in turn frees the first frame
  while the second, allocated later, is still live. The other designs allocate
  their frames at `connect`.
- **6. A precise failure contract.** Every design can say that the work done
  before the operation starts doesn't throw. A `task` coroutine declared
  `noexcept` doesn't throw when it's called, because a failed frame allocation
  then terminates the program, and its error types can leave out
  `exception_ptr`.^[`task`'s `connect` isn't declared `noexcept`
  ([task.members]{.sref}), but with the default `Environment` nothing it does
  can throw; stdexec's `task` declares it `noexcept`.] `any_sender`'s
  constructor can check that the stored sender's `connect` doesn't throw, as
  `function`'s does, and `get` can be declared `noexcept`; stdexec's
  `any_sender_of` doesn't make that check. The hand-written `get_sender` could
  say the same, though as written it doesn't.
- **7. Borrowed state visible in the interface.** A coroutine that is a member
  function borrows `*this`, as `cache::get` does, but nothing in `task`'s type
  says so, and `any_sender`'s type depends only on its completions and
  queries. `function`'s type says so with its reference qualifier; the
  hand-written `get_sender` could too, though as written it doesn't.
- **8a. Declaring an interface.** `task`'s declaration names the value type,
  as the synchronous declaration names its return type. `any_sender`'s type
  and `function`'s proposed form spell out the completion signatures, so each
  takes an alias, such as `any_lookup` or `async_fn`, to read like the
  synchronous declaration; [Future Directions] discusses a standard form of
  `async_fn`. The hand-written `get_sender` makes `get`'s declaration easy once
  it exists, but each new signature needs its own.
- **8b. Writing an implementation.** `task` writes `cache` most simply, as
  [Erasing a Sender Expression] conceded. The other designs all write it with
  the same sender expression, variant sender and all.
- **9. Standard vocabulary.** The hand-written `get_sender` is `function`
  specialized to one signature, so writing one, and saying in it what 6 and 7
  ask, falls to every author, for every signature. stdexec and libunifex each
  have an `any_sender`, and they are different types, but a standard one would
  meet 9, as `function` would.

## Allocation Patterns

Robert Leahy ([@Leahy]) breaks a function call into four steps: prepare the
arguments, pass them, let the function run, and collect the result. In a
synchronous call, the last three happen together. Senders separate all four:
the arguments are prepared when a sender is made, passed when it's connected to
a receiver, the function runs when the operation state is started, and the
result arrives at one of the receiver's completion functions. A sender is the
asynchronous analogue of a nullary callable, and an operation state is the
analogue of an activation frame.

That decomposition locates each design's allocations:

+-------------------------+--------------------+------------------------+------------------------+---------------------+
| Design                  | Allocations        | When                   | Storage chosen by      | Lifetimes nest      |
+:========================+:===================+:=======================+:=======================+:====================+
| *Synchronous call       | One: the stack     | Passing the arguments  | The caller, whose      | Yes                 |
| (reference)*            | frame              |                        | thread owns the stack  |                     |
+-------------------------+--------------------+------------------------+------------------------+---------------------+
| `any_sender`            | Up to two          | Preparing the          | The implementation,    | Only the second's   |
|                         |                    | arguments, and passing | then the caller's      |                     |
|                         |                    | them                   | environment            |                     |
+-------------------------+--------------------+------------------------+------------------------+---------------------+
| Merged `any_sender`     | One                | Preparing the          | The implementation     | No                  |
|                         |                    | arguments              |                        |                     |
+-------------------------+--------------------+------------------------+------------------------+---------------------+
| `task`                  | One                | Preparing the          | Every caller, through  | No                  |
|                         |                    | arguments              | an `allocator_arg`     |                     |
|                         |                    |                        | parameter              |                     |
+-------------------------+--------------------+------------------------+------------------------+---------------------+
| Writing It Yourself     | One                | Passing the arguments  | The caller's           | Yes                 |
|                         |                    |                        | environment            |                     |
+-------------------------+--------------------+------------------------+------------------------+---------------------+
| `function`              | At most one        | Passing the arguments  | The caller's           | Yes                 |
|                         |                    |                        | environment            |                     |

`function` matches the synchronous call in every column, and so does the
hand-written `get_sender`, which is `function` for one
signature.^[The synchronous row is a model of what the abstract machine
provides, not a claim about any implementation. An optimizer may inline a call
and allocate nothing; an asynchronous frame, likewise, may fit in storage the
caller already has.] The nesting claim is along each sequential path; frames on
parallel branches coexist ([Analysis]). The one difference from the reference
row is that the frame is allocated dynamically, and that difference is forced:
an asynchronous operation can outlive the call that started it, so its frame
can't live on the caller's stack.

## Analysis

### The activation frame is the boundary's cost

A synchronous function's declaration names its parameter and return types but
not how much storage its body needs, so the callee, not the caller, provides
its frame.^[This analogy also explains the leak of implementation into interface
that [Returning an Implementation-Specific Sender] showed. Today's concrete
senders are like inline functions: the compiler must see the whole
implementation in order to, among other things, reserve space in the caller's
frame for the callee's.] An asynchronous function separated from its callers
has the same problem and no stack to solve it with, so any design that keeps
the implementation out of the declaration needs one dynamically allocated frame
per call, or must put the frame's size in the interface. `task` and `function`
both pay exactly that one frame, which is the sense in which [@P4088R1] and
[@P4100R1] are right that the allocation pays for the erasure.

Two alternatives try to avoid even that frame. A small buffer in the
operation state, or a fixed capacity that makes a program ill-formed when an
implementation's operation state doesn't fit, as Robert Leahy suggested in
Brno, would each put a size in the interface. An implementation that outgrows
the capacity would need a new interface, as an implementation that changed
structure did in [Returning an Implementation-Specific Sender]. Ruslan
Arutyunyan reported the same experience from Boost: types parameterized on such
a capacity are incompatible across capacities, and changing the capacity breaks
ABI. An inline buffer chosen by the implementation, with no size in the
interface, is a different matter: it's an optimization, permitted but not
required ([Frame Allocation]).

`any_sender`'s other allocation is different in kind. It stores a sender, and a
sender is a value that can be made in one place, moved elsewhere, and connected
later or never, so that allocation follows no pattern a frame allocator could
exploit. Constructing a `function`, by contrast, only copies or moves its
arguments, so it can fail only where passing the same arguments by value to a
synchronous function could.

::: ednote
**Expand:** Extend the analogy to tail calls in a footnote. A factory that only
forwards, returning another `function` of the same type, as a router or a
redirect follower would, makes a tail call, and like C++, `function` doesn't
eliminate it: in the reference implementation, a chain of N such layers keeps N
frames live. `task` does the same, since symmetric transfer bounds stack depth,
not frame count. Because the number of frames is unspecified ([What the Wording
Guarantees]), an implementation may connect such a chain in one frame.
:::

### Where frames come from

Because `function` allocates its frame at `connect`, from the frame allocator
that the caller's environment provides, the choice of allocator travels with
the environment, as every other choice the caller makes does. Nothing in
`kv_store::get`'s declaration mentions it, and no caller between the one that
chooses it and the one that uses it has to pass it along. That is the
propagation [@P4007R3] (section 3) shows `task`'s `allocator_arg` can't
provide, and allocating at `connect` avoids the timing problem that
[@P4172R1] describes, because the environment is known when the frame is
allocated.

Allocating at `connect` also preserves nesting. Making a `function` allocates
nothing, so the algorithm that runs the operations decides the order of their
frames, not the code that makes the senders. Along a sequential path, an
operation connects its successors only as it needs them, and destroys their
operation states before its own is destroyed. In the reference implementation,
a miss through `cache` allocates `cache`'s frame and then `remote_store`'s, and
frees them in the opposite order; two lookups in sequence through `let_value`
free the first lookup's frames before allocating the second's. A frame
allocator for a sequential path can therefore be as simple as a stack, needing
none of the synchronization that a recycling allocator shared by interleaved
operations does.

`task`'s frames are ordered by the calls that make them instead. stdexec's
`exec::sequence` runs its children one after another, connecting each only
after destroying its predecessor's operation state, so `exec::sequence(a(),
b(), c())` frees the frames of three `task`-returning coroutines in the order
`a`, `b`, `c`. C++ leaves the order in which the three calls are evaluated
unspecified, so the order in which those frames are allocated depends on the
compiler: GCC 13 allocated them `c`, `b`, `a`, which nests, and Clang 18
allocated them `a`, `b`, `c`, which doesn't. With either compiler, all three
frames were live before the sequence started. When `a`, `b` and `c` return
`function`s instead, each frame is allocated when `exec::sequence` connects its
child, so with either compiler one frame is live at a time.

Parallel branches are different:

```{.cpp file="fn/lookup_both.cpp" caption="lookup_both.cpp"}
#include "kv_store.hpp"

// looks up "a" and "b" concurrently
auto lookup_both(kv_store const& store) {
  return ex::when_all(store.get("a"), store.get("b"));
}
```

With `cache` as the store and both keys missing, connecting the `when_all`
allocates both `cache` frames, and starting it allocates a `remote_store` frame
for each branch. Each branch frees its frames when its own lookup finishes, so
in the reference implementation one branch's `cache` frame can be freed while
the other branch's `remote_store` frame, allocated later, is still live. Frames
on parallel branches coexist rather than nest. Since each child's frame allocator
comes from its environment, a parallel algorithm could give each branch its own
allocator; designing that belongs to the frame-allocation paper that [Frame
Allocation] describes.

### Where `task` is better

[Erasing a Sender Expression] conceded that `task` writes `cache` most simply.
That is the one requirement on which `function` loses, and it loses to a
design that fails five others. A coroutine needs no variant sender because its
control flow chooses between the hit and the miss. A language extension that let a
coroutine return a `function`, allocating its frame at `connect` from the
caller's frame allocator, could close the gap; this paper doesn't propose one.

## Conclusion

The use case this paper addresses is declaring an asynchronous function whose
definition lives elsewhere, including a virtual function with many
definitions. For that use, `function` meets every requirement, with
ergonomics that match `any_sender`'s and trail `task`'s for writing
implementations. `task` writes implementations best, but can't be used where
coroutines aren't available, can't let the caller's environment choose its
frame allocator, and can't say that it borrows an object.

Neither `function` nor `any_sender` subsumes the other. `function` represents a
pending call: its type says what the call takes and borrows, and it allocates
nothing until it's connected. `any_sender` represents a sender value whose
origin its holder needn't know, such as a sender passed between components and
stored, and it hides the argument types that `function` names. `any_sender` can
serve as an interface's return type, at the cost of an extra allocation and
without saying what the call borrows, which is how the designs compare
above. A `function` can erase a sender that already exists only by borrowing
it. A reference-qualified `function` can take the sender as its implicit object
argument, and its type then says the sender is borrowed, as `kv_store::get`'s
type says the store is. Owning the sender would take a curried argument of the
sender's type, which `function`'s type would name. This
paper proposes `function` because the problem it addresses is the declaration
of asynchronous functions, and takes no position on whether the standard should
also have an `any_sender`.

Settled in that context, the allocation question has a clear answer: the
frame is the one allocation the boundary requires, and its size can't be part of
the interface, so any buffer that avoids allocating small frames is a quality
of implementation. That buffer has a cost at scale. Every in-flight operation
carries its `function`'s fixed-size operation state, which in the reference
implementation holds a 64-byte inline buffer, wasted whenever the frame doesn't
fit, beside a vtable pointer. A program with a hundred thousand outstanding
operations pays for that buffer on each one. The proposed wording recommends at
most one allocation and requires no buffer, so an implementation can omit it.

This paper therefore proposes `std::execution::function`, a class template
whose specializations are type-erasing senders for declaring asynchronous
functions, and `std::execution::get_frame_allocator`, an environment query
whose result, when present, allocates their frames. [Interface Discussion]
describes `function`'s interface, and [Frame Allocation] the query.

# Interface Discussion

The examples so far declare `function`s through `async_fn`, the paper-local
alias from [A Third Way]. This section describes the type that alias names. A
specialization of `function` takes up to four template arguments, in this order:

1. a function type whose return type is `sender_tag`, describing the call;
2. a specialization of `completion_signatures`, listing how the operation can
   complete;
3. optionally, a specialization of `queries`, listing what the operation needs
   from the caller's environment; and
4. optionally, a specialization of `attrs`, listing where the operation
   completes.

`async_fn<R(Args...) const &>` names
`function<sender_tag(Args...) const &, completion_signatures<set_value_t(R), set_error_t(exception_ptr), set_stopped_t()>>`.
The subsections below take the arguments in turn, then the factory that defines
each implementation, and end with the running example's interface written
without the alias.

## The Call

The first argument is the type of the call that a `function` represents. Its
parameter types are the types of the curried arguments, which the constructor
stores and `connect` passes to the factory. Its return type is `sender_tag`,
because calling the function produces a sender, and a sender can complete in
more ways than a return type can describe; the second argument lists them.
Other return types are left free for a form, not proposed here, that computes
the completions from a value type ([Future Directions]).

The constructor takes a parameter declared as `T` as `T const&` when `T` is
trivially copy-constructible and trivially move-constructible, and as `T&&`
otherwise. An lvalue argument is therefore accepted, and copied, exactly when
writing `std::move` would change nothing. An `int` can be passed as it is, but a
`std::string` lvalue must be moved, or copied explicitly with `auto(s)`, so a
costly copy is never made silently. This departs from the synchronous analogy,
where a by-value parameter copies any lvalue. Both traits are required because
binding to `T const&` copies even an rvalue, which is wrong for a type whose
move constructor isn't trivial. No trait says whether a copy is cheap, so the
rule errs toward asking for a `std::move`.

The analogy breaks down in one more place. A `function` is a sender, and senders
are moved, so every curried argument must be move-constructible, while a
synchronous function can take an immovable type by value.

A `noexcept` function type, such as `sender_tag(std::string) const & noexcept`,
makes a promise about connecting the `function`. [The Exception Contract of
`connect`] explains what it promises, how the constructor checks it, and how it
relates to the caller's frame allocator. The reference qualifier is the subject
of [Member Functions].

## Completion Signatures

The second argument lists every way the operation can complete, and a
`function` adds nothing to it. A `function` whose signatures leave out
`set_error_t(exception_ptr)` can't report an exception, so its constructor
rejects a factory whose sender might complete that way, and an implementation
must catch its exceptions and report them as one of the declared errors, as
[Full Control] shows. An implementation may complete in fewer ways than the type
declares.

The order of the signatures doesn't matter. Two `function` types whose
signatures differ only in order are the same type, so an interface's type
doesn't depend on the order in which its author wrote them. The same holds for
`queries` and `attrs`.

Since the type fixes no completions in advance, a `function` can declare any
asynchronous function that a sender can represent (requirement 3), with several
value completions, value completions with several arguments, error types other
than `exception_ptr`, or no `set_stopped_t()`. For example, a read from a
network connection can fail after filling part of its buffer, and that partial
success is a value of its own:

```{.cpp file="net/read.hpp" caption="read.hpp"}
#include <exec/function.hpp>
#include <stdexec/execution.hpp>

#include <cstddef>
#include <span>
#include <system_error>

namespace ex = STDEXEC;

// A read into a buffer from a connection that the read borrows. It completes
// with the filled buffer, with an error and the part of the buffer filled
// before it, or with an error alone if it read nothing. A read cancelled after
// filling part of the buffer completes with an error and that part; one
// cancelled before reading anything completes as stopped.
using pending_read = exec::function<
    ex::sender_tag(std::span<std::byte>) &,
    ex::completion_signatures<
        ex::set_value_t(std::span<std::byte>),
        ex::set_value_t(std::error_code, std::span<std::byte>),
        ex::set_error_t(std::error_code),
        ex::set_stopped_t()>>;
```

A `task` can't declare this read, because it has one value completion, so both
successes would have to share a value type. A coroutine can't await it,
either. Awaiting a sender requires it to have at most one value completion
([execution.syn]{.sref}), and turns an `error_code` on its error channel into a
thrown `system_error` ([exec.general]{.sref}, [exec.as.awaitable]{.sref}). A
coroutine that avoids exceptions therefore needs all three outcomes merged into
one value completion, such as `set_value_t(std::error_code,
std::span<std::byte>)`, which `auto [ec, buffer] = co_await ...` decomposes.
That merged form follows from how coroutines await senders, not from what
network code needs. A `function` can declare it, or keep the outcomes apart,
and the interface's author chooses.

## Required Queries

A `function`'s implementation is connected to a receiver that erases the
caller's, and that receiver's environment answers only `get_frame_allocator`
([Frame Allocation]) and the queries that the third argument declares. Nothing
else in the caller's environment reaches the implementation, not even the stop
token. Each declared query is a function type, `Return(Query, Args...)`,
optionally `noexcept`, and the caller's environment must answer `Query` with
arguments of types `Args...`, with a result convertible to `Return`, and
without throwing if the declared type is `noexcept`. In an environment that
doesn't, the `function` has no completion signatures, so it can't be connected.

The erased environment's type is fixed by the `function`'s type, so it can only
answer queries whose result types that type names; what remains to decide is
what an interface declares by default. This paper declares nothing by default:

1. **A forwarded query has a cost.** Each one is an indirect call through the
   erased receiver, and one whose result must be adapted can cost more.
   Declaring a query is how an interface's author chooses to pay for it.
2. **A forwarded query is a dependence.** An implementation that can see a
   query can rely on it, which makes it something every caller must provide.
   The type says so, as its parameter types say what every caller must pass.
3. **The caller's domain doesn't reach the implementation.** A query such as
   `get_scheduler` would let the caller's scheduler, and with it the caller's
   domain, choose how the implementation's sender is transformed. Keeping it
   out unless declared is part of what [Domains and Type Erasure] discusses.

Whether a convenience form should forward the stop token by default is one of
the open questions in [Future Directions].

The fourth argument declares where the operation completes, as completion
domains. `attrs<D(get_completion_domain_t<set_value_t>)>` says that the
implementation's sender completes successfully in domain `D`; the constructor
rejects a factory whose sender doesn't, and the `function` reports `D` to the
algorithms it's passed to. Without `attrs`, a `function` makes no claim about
where it completes. [Domains and Type Erasure] discusses what a `function`
should report.

## Member Functions

R0 accepted any trivially copyable callable small enough to fit the factory's
storage, whose size was up to the implementation. A lambda that captures `this`
qualifies, so a `function` could borrow an object without its type saying so. R1
lets the type say so with a reference qualifier, as a member function's
declaration does. A `function` whose type is `sender_tag(Args...) const &`
represents a call to a const member function. Its constructor takes the object,
which must be an lvalue, before the curried arguments, and stores a pointer to
it; `connect` passes it to the factory as a const reference, before the curried
arguments. [`function`]'s `cache::get` passes `*this` that way, and its factory
takes `self`. `sender_tag(Args...) &` likewise represents a call to a non-const
member function, and as with a synchronous member function, a non-const lvalue
can be passed to a `const &` `function`.

The type says that the call borrows an object but not the object's class, which
the constructor erases along with the factory. Every override of
`kv_store::get` therefore returns the same type, while each override's factory
receives the object as its own class, such as `cache const&`, and reaches
private members without a cast.

Three kinds of qualifier are rejected. `&&` and `const &&` would borrow an
object that is about to expire, so `auto pending = make_store().get(key);`
would leave `pending` pointing at a destroyed store. A `const` member function
without a reference qualifier can be called on an rvalue too, so it would reopen
the same hole. `volatile` forms are rejected as well.

Explicit object parameters need no special support. One of reference type
behaves as the reference-qualified forms do. One taken by value corresponds to a
leading curried parameter, `sender_tag(Object, Args...)`, so the `function` owns
a copy of the object; an `&&` form that moved the object in would add only a
spelling. When the explicit object parameter's type is deduced, the
`function`'s type depends on it, so the return type is written in terms of it:

```{.cpp file="self/message.hpp" caption="message.hpp"}
#include <exec/function.hpp>
#include <stdexec/execution.hpp>

#include <cstdio>
#include <exception>
#include <string>
#include <utility>

namespace ex = STDEXEC;

using sent = ex::completion_signatures<ex::set_value_t(),
                                       ex::set_error_t(std::exception_ptr),
                                       ex::set_stopped_t()>;

// sends m's body, here to standard output
template <class Message>
auto transmit(Message m) {
  return ex::just() |
         ex::then([m = std::move(m)] { std::fputs(m.body.c_str(), stdout); });
}

// A message that sends a copy of itself, so the original can change or be
// destroyed while the copy is in flight. A message of a derived type sends a
// copy of its own type.
struct message {
  std::string body;

  template <class Self>
  exec::function<ex::sender_tag(Self), sent> send(this Self self) {
    return exec::function<ex::sender_tag(Self), sent>(
        std::move(self), [](Self self) { return transmit(std::move(self)); });
  }
};
```

Calling `send` on an `urgent_message` derived from `message` returns a
`function<sender_tag(urgent_message), sent>`. A forwarding explicit object
parameter, `this Self&& self` with `sender_tag(Self)`, borrows an lvalue through
a curried parameter of reference type and owns an rvalue moved into the
`function`, so nothing dangles, and the type says which. An explicit object
member function can't be virtual, so virtual interfaces such as `kv_store` use
the reference-qualified forms.

## Factories

`connect` invokes the factory with the object, if any, and the curried
arguments, and connects the sender that the factory returns. The factory must be
stateless. It can be a pointer to a function, a pointer to a member, or an
empty, trivially copyable callable, such as a lambda with no captures or a
customization point object like `just`. It's invoked as a const lvalue, with the curried
arguments as rvalues. Statelessness matters for two reasons:

1. **State in the factory would be state the type doesn't show.** A lambda that
   captures `this` is the hidden borrow that [Member Functions] removes. With a
   stateless factory, the object and the curried arguments are the only state a
   `function` holds, and its type names both, so the reference qualifier is a
   guarantee rather than an annotation.
2. **Every stateless factory fits on every implementation.** R0's factory
   storage also had a fixed size, so constructing a `function` allocated
   nothing of its own (requirement 5a), but whether a given capturing lambda
   fit depended on the implementation's choice of size. Storage as large as the
   largest pointer to a member holds any stateless factory, so a factory that
   one implementation accepts, every implementation accepts.

A factory can return any sender, so an implementation can be a coroutine even
though the interface isn't one. `task` is a sender, so [`task`]'s `cache::get`
can sit behind [A Third Way]'s interface:

```{.cpp file="fn/coro_cache.cpp" caption="cache.cpp"}
#include "cache.hpp"

#include <utility>

// starts the coroutine wherever it's started, so the interface needn't declare
// a scheduler query
struct start_inline {
  using start_scheduler_type = ex::inline_scheduler;
};

cache::cache(kv_store const& backing) : backing_(&backing) {}

async_fn<std::optional<std::string>(std::string) const &>
cache::get(std::string key) const {
  return async_fn<std::optional<std::string>(std::string) const &>(
      *this, std::move(key),
      [](cache const& self, std::string key)
          -> ex::task<std::optional<std::string>, start_inline> {
        if (auto value = self.entries_.find(key)) {
          co_return value;
        }
        auto value = co_await self.backing_->get(key);
        if (value) {
          self.entries_.insert(std::move(key), *value);
        }
        co_return value;
      });
}
```

This version reads like the synchronous one, which [Where `task` is better]
conceded a sender expression can't, but it pays in allocations. The
coroutine's frame comes from `task`'s allocator rather than the caller's frame
allocator, and so does the frame of the backing store's `function`, which the
coroutine connects in its own environment. In the reference implementation, a
hit allocates twice and a miss three times, and only `cache`'s `function`
frame comes from the caller's frame allocator. That trade is the
implementation's to make; callers of `kv_store::get` can't tell which version
they're calling.

## Full Control

`async_fn` fixes the error type to `exception_ptr` and declares no queries.
Here is `kv_store` with every argument chosen, as an interface for code that
reports failure with error codes might be:

```{.cpp file="final/kv_store.hpp" caption="kv_store.hpp"}
#include <exec/function.hpp>
#include <stdexec/execution.hpp>

#include <optional>
#include <string>
#include <system_error>

namespace ex = STDEXEC;

// A lookup in a borrowed store. Neither calling get nor connecting the lookup
// throws, the lookup reports failure as an error code, and a caller can stop it
// with an inplace_stop_token.
using lookup = exec::function<
    ex::sender_tag(std::string) const & noexcept,
    ex::completion_signatures<ex::set_value_t(std::optional<std::string>),
                              ex::set_error_t(std::error_code),
                              ex::set_stopped_t()>,
    exec::queries<ex::inplace_stop_token(ex::get_stop_token_t) noexcept>>;

struct kv_store {
  virtual ~kv_store() = default;
  virtual lookup get(std::string key) const noexcept = 0;
};
```

`get` is `noexcept` as well, since constructing a `function` only moves its
arguments. Every implementation must now report failure as a
`std::error_code`, so the two implementations share an adaptor that turns their
exceptions into error codes:

```{.cpp file="final/error_codes.hpp" caption="error_codes.hpp"}
#include <stdexec/execution.hpp>

#include <concepts>
#include <exception>
#include <new>
#include <system_error>

namespace ex = STDEXEC;

// the error code for an exception these implementations can throw
inline std::error_code error_code_from(std::exception_ptr error) noexcept {
  try {
    std::rethrow_exception(error);
  } catch (std::bad_alloc const&) {
    return std::make_error_code(std::errc::not_enough_memory);
  } catch (std::system_error const& e) {
    return e.code();
  }
  // anything else escapes this noexcept function and terminates the program
}

// an adaptor that reports exceptions as error codes and passes error codes on
inline auto report_errors_as_error_codes() noexcept {
  return ex::let_error([]<class Error>(Error const& error) noexcept {
    if constexpr (std::same_as<Error, std::exception_ptr>) {
      return ex::just_error(error_code_from(error));
    } else {
      return ex::just_error(error);
    }
  });
}
```

The headers of `remote_store` and `cache` differ from [A Third Way]'s only in
`get`'s declaration. Their definitions use the adaptor last:

```{.cpp file="final/remote_store.cpp" caption="remote_store.cpp"}
#include "error_codes.hpp"
#include "remote_store.hpp"

#include <chrono>
#include <utility>

remote_store::remote_store(exec::timed_thread_scheduler latency,
                           std::map<std::string, std::string> data)
    : latency_(latency), data_(std::move(data)) {}

lookup remote_store::get(std::string key) const noexcept {
  return lookup(
      *this, std::move(key),
      [](remote_store const& self, std::string key) noexcept {
        return exec::schedule_after(self.latency_,
                                    std::chrono::milliseconds{5}) |
               ex::then([data = &self.data_, key = std::move(key)] {
                 std::optional<std::string> value;
                 if (auto it = data->find(key); it != data->end()) {
                   value = it->second;  // copying the value can throw
                 }
                 return value;
               }) |
               report_errors_as_error_codes();
      });
}
```

```{.cpp file="final/cache.cpp" caption="cache.cpp"}
#include "cache.hpp"
#include "error_codes.hpp"

#include <exec/variant_sender.hpp>

#include <utility>

cache::cache(kv_store const& backing) : backing_(&backing) {}

lookup cache::get(std::string key) const noexcept {
  return lookup(
      *this, std::move(key), [](cache const& self, std::string key) noexcept {
        return ex::just(std::move(key)) |
               ex::let_value([&self](std::string const& key) {
                 auto miss = [&] {
                   return self.backing_->get(key) |
                          ex::then([&self, &key](
                                       std::optional<std::string> value) noexcept {
                            if (value) {
                              try {
                                self.entries_.insert(key, *value);
                              } catch (...) {
                                // caching is best-effort; the lookup succeeds
                              }
                            }
                            return value;
                          });
                 };
                 using result = exec::variant_sender<
                     decltype(ex::just(std::optional<std::string>())),
                     decltype(miss())>;
                 // a hit copies the value and a miss copies the key, so either
                 // can throw
                 if (auto value = self.entries_.find(key)) {
                   return result(ex::just(std::move(value)));
                 }
                 return result(miss());
               }) |
               report_errors_as_error_codes();
      });
}
```

The stop token that the interface declares reaches `remote_store`'s timer, even
through `cache`, so a caller that stops a lookup stops the wait for the
network. Three other things in these implementations follow from the interface
rather than from what the implementations do:

- **`noexcept` describes connecting, not the operation.** A hit copies the
  cached value after the operation starts, and if the copy fails, the failure
  arrives as `set_error`, like any other asynchronous failure.
- **Fallible work belongs after the operation starts.** Both factories only
  move their arguments and build senders. The copies, the cache insertion and
  the call to the backing store all happen inside the sender, where a failure
  becomes a completion.
- **The interface's author chose the contract for every implementation.** Both
  implementations must translate exceptions, and `cache` must also handle a
  failure to allocate the backing store's frame. `let_value` connects the
  backing store's `function` after the operation has started, so it reports
  that failure as an `exception_ptr`, which the adaptor turns into
  `errc::not_enough_memory`.

# Frame Allocation

A `function`'s only allocation is its frame, the storage for the operation
state of the sender that its factory returns, and [Where frames come from]
argued that the caller's environment should choose where that frame comes
from. This paper proposes one query for making that choice,
`get_frame_allocator`, and specifies how `function` uses its answer. The rest
of a frame-allocation design is left to a later paper.

## The Query

`get_frame_allocator` asks an environment for the allocator that activation
frames should come from. As with `get_allocator`, its result must be a
*`simple-allocator`*, and it is a forwarding query, so an adaptor that forwards
its receiver's environment passes the choice on to its children. A caller
chooses a frame allocator the way it chooses anything else in its environment:

```{.cpp file="fn/lookup_in.cpp" caption="lookup_in.cpp"}
#include "kv_store.hpp"

#include <exec/get_frame_allocator.hpp>

#include <memory_resource>
#include <string>
#include <utility>

// looks up key, allocating the lookup's frames from frames
auto lookup_in(kv_store const& store, std::string key,
               std::pmr::memory_resource& frames) {
  return store.get(std::move(key))
       | ex::write_env(ex::prop(exec::get_frame_allocator,
                                std::pmr::polymorphic_allocator<>(&frames)));
}
```

Neither `kv_store::get`'s declaration nor `cache`'s implementation mentions
the allocator. On a miss, `remote_store`'s frame comes from `frames` too,
because the environment that `cache`'s implementation sees answers
`get_frame_allocator` ([Required Queries]).

The query is separate from `get_allocator` because its answer is used only for
frames, and frames are allocated in a pattern that other allocations don't
follow. Along a sequential path, frames nest (requirement 5c), and an allocator
can exploit that. Nothing promises the same of `get_allocator`'s answer, which
serves whatever an operation allocates. `spawn`, for example, allocates its
operation state with it ([exec.spawn]{.sref} paragraph 9), and that operation
state outlives the code that spawned it. A separate query lets a program give
its frames an allocator that relies on their pattern without auditing every
other use of `get_allocator`. [@P4172R1] (section 6.3) draws the same line for
coroutines, whose frame allocator is used for nothing but frames.

The reference implementation also accepts a `std::pmr::memory_resource*` as
the query's result. This paper keeps R0's requirement of a
*`simple-allocator`*; whether to accept a memory resource as well is a question
for the frame-allocation paper.

each branch its own allocator would change. Discuss the result type at more
length: *`simple-allocator`* versus `std::pmr::memory_resource*`, and what each
costs a caller who already has the other.
:::

## What the Wording Guarantees

The proposed wording guarantees the limits of `function`'s allocation and
leaves its mechanism open. It specifies:

1. **Where the frame comes from.** `connect` takes its frame allocator from
   `get_frame_allocator` on the receiver's environment whenever that
   environment answers the query. That is how the caller chooses (requirement
   5b).
2. **Nothing is allocated before `connect`.** Constructing, copying or moving a
   `function` allocates nothing of its own, so making a pending call costs what
   passing its arguments by value would (requirement 5a).
3. **The frame is freed with the operation state.** The frame is deallocated,
   through the allocator that allocated it, before the operation state's
   destructor returns. That ties the frame's lifetime to the operation's, which
   is what makes frames nest along sequential paths (requirement 5c), and lets
   a caller destroy its frame allocator once the operations that use it are
   destroyed.
4. **A failed allocation is reported by `connect`.** If allocating the frame
   throws, `connect` exits with that exception. Whether connecting can throw
   therefore depends on the caller's frame allocator as well as on the
   `function`'s type; [The Exception Contract of `connect`] gives the rule.
5. **The operation state is constructed in the frame, not by the allocator.**
   `connect` allocates raw storage and constructs the implementation's
   operation state in it directly, without uses-allocator construction.
   Uses-allocator construction would offer the frame allocator to the operation
   state for its own allocations, mixing frames with the allocations that
   `get_allocator` serves.

It leaves unspecified:

1. **Whether a frame is allocated at all.** An implementation can hold a small
   operation state inline instead; the reference implementation does so for
   operation states of up to 64 bytes. Whether that buffer is worth its cost
   at scale ([Conclusion]) is a question of quality of implementation.
2. **How many allocations a `function` makes.** Recommended practice, not a
   requirement, says at most one. A requirement would have to say which
   allocations are the `function`'s own, and the sender that the factory
   returns allocates as it likes, as the `task` in [Factories] did.
3. **What happens when the caller chooses nothing.** In an environment that
   doesn't answer `get_frame_allocator`, the reference implementation uses
   `get_allocator` and then `std::allocator`. Leaving the fallback open lets
   the frame-allocation paper choose a default without changing `function`,
   and a program that cares where its frames come from can say so in its
   environment.
4. **The type of the frame allocator that the implementation sees.** The
   environment that the implementation sees always answers
   `get_frame_allocator` ([Required Queries]), but the caller's allocator type
   can't appear in the `function`'s type, so the answer is an allocator of
   unspecified type that allocates from wherever the `function`'s own frame
   came from. In the reference implementation, it's a
   `std::pmr::polymorphic_allocator<std::byte>`. An interface that needs a
   particular type can declare the query, as it would any other, at the cost of
   requiring every caller to answer it.

::: ednote
**Expand:** Give each item its sentence of wording, as it will appear in
`connect`'s *Effects* and the *Recommended practice* paragraph. Say where the
reference implementation departs from item 5. Show the allocations that the
running example makes on a hit and on a miss.
:::

## Frame Allocators for Coroutines

`get_frame_allocator` is inspired by the frame allocator that Vinnie Falco
*et al.* designed for coroutines. [@P4003R3] (section 3.5) argues that the
frame allocator must be a first-class part of an execution model. It has a
default that the application can replace, and it reaches every frame in a chain
of calls without any signature mentioning it. [@P4172R1] (section 6.3)
explains why a frame allocator can be fast, since frame sizes repeat and
lifetimes nest, and section 6.3.1 leaves the allocation strategy to
implementations; its section 11.1 notes that `exec::function`, this paper's
reference implementation, adopted the same pattern. `get_frame_allocator`
shares those aims: one allocator for frames, chosen by the caller, reaching
every frame without appearing in signatures, with the strategy left open.

The designs differ in when a frame is allocated, and that decides how the
allocator is delivered. A coroutine's frame is allocated by its promise's
`operator new` before the coroutine can see any environment, which [@P4127R0]
calls the frame allocator timing problem. The coroutine design therefore
delivers the allocator before the call, either as an `allocator_arg` argument
or through state that `operator new` reads out of band ([@P4127R0] section 4).
[@P4003R3] (section 4.5) leaves the out-of-band storage to implementations,
and [@P4172R1] (section 8.2) describes thread-local storage as the default. A
`function`'s frame is allocated at `connect`, when the receiver's environment
is known, so the environment answers the query directly and the call needs no
state outside it.

[@P4127R0] (section 6) shows that the parameter list and ambient state are the
only ways to deliver an allocator to a coroutine's `operator new`, and for
coroutines that conclusion is correct. A `function` escapes it by allocating
later. Every `function` in a chain looks the allocator up in its own receiver's
environment when it's connected, so the caller's choice reaches every
`function`'s frame, not only the first, which [@P4127R0] (section 5.8) shows a
wrapper at the boundary between senders and coroutines can't do. [@P4172R1]
(section 11.1) counts the lack of a frame-allocator propagation mechanism among
the reasons sender/receiver suits I/O less well; `get_frame_allocator`, looked
up at `connect`, is that mechanism.

The designs also differ in type. [@P4003R3] (section 3.5)
allows a frame allocator to be either an allocator or a
`std::pmr::memory_resource*`, but its protocol carries a
`std::pmr::memory_resource*` (section 4.1), while `get_frame_allocator`
returns an allocator, as `get_allocator` does.

::: ednote
**Expand:** Describe the coroutine design in its own terms (its environment,
its execution context's default allocator, its two-phase launch, its recycling
allocator and the measurements in [@P4003R3]) before comparing, and say where
each design could adopt the other's mechanism.
:::

## Left to a Later Paper

The frame-allocation paper would cover what this one leaves out: how a parallel
algorithm gives each branch its own frame allocator ([Where frames come
from]), which allocation strategies suit frames, what types the query may
return, what `function` falls back to when the caller chooses nothing, and,
ideally, a frame-allocation design shared by coroutines and senders.

::: ednote

# The Exception Contract of `connect`

Requirement 6 asks that a type can say the work done before an operation starts
doesn't throw. For a `function`, that work is two steps. Calling `get`
constructs the `function`, which only moves its arguments, so `get`'s
declaration can say `noexcept`, as [Full Control]'s does. Connecting is the
step that the `function`'s own type must describe, because generic algorithms
compute whether their own `connect` throws from whether their children's does.
This section says what a `noexcept` function type promises about connecting,
when `connect` is `noexcept`, how the constructor checks the promise, and what
it trusts instead of checking.

## Who Answers for What

Three parties decide what happens when a `function` is connected. The
interface's author writes its type, which fixes the call's parameters, the
completion signatures, the queries that the implementation may make of the
caller's environment, the domains in which the operation completes, and
whether the type is `noexcept`. The implementer writes a factory, which the
constructor checks against that type. The caller chooses the receiver, and with
it the environment, including the frame allocator.

One principle divides the contract between them. What the type fixes is its
author's responsibility, and what the caller chooses appears in `connect`'s
exception specification. A `noexcept` function type therefore promises that
invoking the factory and connecting the sender it returns don't throw, except by
failing to allocate a frame. The frame comes from the caller's allocator, which
the type can't name, so whether allocating it can fail is the caller's to say.

## The Rule

Each of `function`'s two `connect` overloads is `noexcept` exactly when nothing
it does can throw:

- `connect() &&` is `noexcept` when the function type is `noexcept` and
  allocating from the frame allocator chosen from the receiver's environment
  doesn't throw.
- `connect() const &` copies the curried arguments first, so it also requires
  them to be nothrow copy-constructible.

`connect() &&` passes the curried arguments to the factory as rvalues, so any
move they need happens as part of invoking the factory, which the constructor
checks. Neither overload depends on the receiver itself. Receivers are nothrow
move-constructible ([exec.recv.concepts]{.sref}), and a program is ill-formed,
no diagnostic required, if `connect`'s exception specification differs between
two receivers whose environments have the same type ([exec.connect]{.sref}), so
the environment is all the rule could depend on.

[Full Control]'s `lookup` is `noexcept`, but connecting one through
`lookup_in` can throw, because `std::pmr::polymorphic_allocator`'s `allocate`
reports failure by throwing. A caller that treats running out of memory for
frames as fatal, as running out of stack is, can say so with an allocator of
its own:

```{.cpp file="final/lookup_or_terminate.cpp" caption="lookup_or_terminate.cpp"}
#include "kv_store.hpp"

#include <exec/get_frame_allocator.hpp>

#include <cstddef>
#include <memory_resource>
#include <string>
#include <utility>

// An allocator for frames that can't report failure. allocate is noexcept, so
// if the resource throws, the program terminates.
template <class T>
struct fatal_allocator {
  using value_type = T;

  explicit fatal_allocator(std::pmr::memory_resource& frames) noexcept
      : frames(&frames) {}

  template <class U>
  fatal_allocator(fatal_allocator<U> const& other) noexcept
      : frames(other.frames) {}

  T* allocate(std::size_t n) noexcept {
    return static_cast<T*>(frames->allocate(n * sizeof(T), alignof(T)));
  }

  void deallocate(T* p, std::size_t n) noexcept {
    frames->deallocate(p, n * sizeof(T), alignof(T));
  }

  friend bool operator==(fatal_allocator, fatal_allocator) = default;

  std::pmr::memory_resource* frames;
};

// looks up key, allocating the lookup's frames from frames, and terminates if
// they can't be allocated
auto lookup_or_terminate(kv_store const& store, std::string key,
                         std::pmr::memory_resource& frames) {
  return store.get(std::move(key))
       | ex::write_env(ex::prop(exec::get_frame_allocator,
                                fatal_allocator<std::byte>(frames)));
}
```

Connecting an rvalue `lookup` in that environment is `noexcept`. Connecting an
lvalue `lookup` isn't, because it copies the key first. The rule needs nothing
more for an environment that doesn't answer `get_frame_allocator`. `connect`
then allocates from the fallback that [What the Wording Guarantees] leaves to
the implementation, and in choosing the fallback, the implementation also
decides whether allocating from it can throw. The reference implementation's
fallback ends with `std::allocator`, whose `allocate` throws, so there its
`connect` can throw.

A frame allocated after the operation starts is a different matter, and the
interface's author has already settled it. [Full Control]'s `cache` connects
the backing store's `lookup` inside `let_value`, after its own operation has
started, so a failure to allocate the backing store's frame arrives as a
completion, which `cache` reports as `errc::not_enough_memory`.

The simplest alternative to this rule is a `connect` that is potentially
throwing for every `function`. No `function` could then promise a
non-throwing `connect`, whatever its type and whatever the caller's allocator,
so requirement 6 would go unmet, and a sender built from a `function` could
never be connected in code that can't handle an exception. [Open Questions and
Polls] asks LEWG to choose between the two.

## Choosing a Failure Policy

Frame allocation is the one failure a `noexcept` function type can't rule out,
and a program might want any of three things when it happens. It might want to
terminate, to have `connect` throw, or to have the operation complete with an
error. This paper leaves the choice between the first two to the frame
allocator, because the caller knows which it wants and the interface's author
doesn't. One interface can serve both kinds of caller. A server that sheds load
when memory runs short wants an exception it can catch where it accepts work,
while an embedded program that sizes its frame arena in advance treats running
out as a bug. The third is future work ([Reporting Allocation Failure as a
Completion]).

A simpler policy was considered. Allocating a stack frame isn't expected to
fail, and if frame allocation weren't either, a failure would always terminate
and `connect` would be `noexcept` for every `noexcept` function type. That
policy makes every `noexcept` `function` easy to compose, but it decides for
every caller of every interface, so this paper doesn't propose it. A caller
that wants it gets it from an allocator like `fatal_allocator`.

A codebase that never throws, and uses one policy everywhere, has another way
to the same result. Its interfaces can name a concrete, non-throwing allocator
type, and a `noexcept` `task` coroutine that takes that allocator through
`allocator_arg`, or an `any_sender` that allocates from it, is then `noexcept`
to call and to connect with no help from the environment. The cost is
requirement 5b's: the allocator appears in every signature, and every caller in
between must pass it along ([@P4007R3] section 3).

## Checking the Promise

The constructor checks a `noexcept` function type's promise against the factory
it's given. A check that passes by mistake can turn an exception into a call to
`std::terminate`, and one that fails by mistake rejects a correct program, so
the check must be exact. What can be checked exactly depends on what connecting
does.

A `function`'s `connect` invokes the factory and connects the sender that the
factory returns to a receiver that erases the caller's. `std::execution::connect`
doesn't call the sender's `connect` member directly. It first passes the sender
and the receiver's environment to `transform_sender`, and calls `connect` on the
result ([exec.connect]{.sref}). `transform_sender` lets the domains associated
with the sender and the environment replace the sender
([exec.snd.transform]{.sref}). A domain for other hardware does so; nvexec's
`stream_domain`, for example, replaces standard algorithms with versions that
run on a GPU. Connecting the factory's sender therefore connects either that
sender, if no domain transforms it, or whatever a domain makes of it.

Three policies could check the promise:

1. **Check everything.** Require that neither the transformation nor the
   transformed sender's `connect` throws.
2. **Trust everything.** Check only that invoking the factory doesn't throw.
3. **Check what is exact.** Require that invoking the factory with the curried
   arguments as rvalues doesn't throw and, if no domain transforms the sender
   it returns, that the sender's `connect` doesn't throw. Trust a
   transformation, and the transformed sender's `connect`. If either throws,
   the exception propagates from the `function`'s `connect`, and if that
   `connect` is `noexcept` ([The Rule]), `std::terminate` is called. This
   paper proposes this policy.

They differ on four kinds of factory:

+-------------------------------+-------------------+------------------------+-------------------+
| The factory returns           | Check everything  | Trust everything       | Check what is     |
|                               |                   |                        | exact             |
+:==============================+:==================+:=======================+:==================+
| A sender that no domain       | Rejected          | Accepted               | Rejected          |
| transforms, whose `connect`   |                   |                        |                   |
| can't throw but isn't         |                   |                        |                   |
| declared `noexcept`           |                   |                        |                   |
+-------------------------------+-------------------+------------------------+-------------------+
| A sender that no domain       | Rejected          | Accepted, and may      | Rejected          |
| transforms, whose `connect`   |                   | terminate if the copy  |                   |
| copies a `std::vector`        |                   | fails                  |                   |
+-------------------------------+-------------------+------------------------+-------------------+
| A sender that a domain        | Rejected          | Accepted               | Accepted          |
| transforms, such as one bound |                   |                        |                   |
| for `stream_domain`           |                   |                        |                   |
+-------------------------------+-------------------+------------------------+-------------------+
| Another `noexcept` `function` | Accepted          | Accepted               | Accepted          |
+-------------------------------+-------------------+------------------------+-------------------+

In the first two rows, the people who wrote the type and the factory can fix
what's rejected. The implementer chose the sender, and can choose one whose
`connect` is declared `noexcept`, or the author can drop `noexcept` from the
type. Trusting these senders would let the second row's real hazard through
with no diagnostic. In the third row, neither can fix it, because the
transformation belongs to the domain. nvexec's per-algorithm transformations,
for example, aren't declared `noexcept`, though they only build a new sender.
Checking everything would make a `noexcept` `function` that wraps GPU work
impossible to write, whatever its author did. The fourth row agrees across the
policies only because of how the check treats frame allocation, which the next
subsection describes.

Every check is a *Constraint* on the constructor, as `move_only_function`'s
are, so `is_constructible_v` answers truthfully and generic code can ask
whether a factory suits a `noexcept` `function` type. A *Recommended practice*
paragraph asks implementations to say which requirement a rejected factory
doesn't meet.

### Frame Allocation in the Check

An inner `function` allocates its frame through the frame allocator that the
outer `function`'s erased receiver provides. A type that declares a
`get_frame_allocator` query names that allocator's type, and if its `allocate`
is `noexcept`, a nested `noexcept` `function` passes the check as it stands,
but every caller must then provide that type ([Required Queries]). Otherwise,
the allocator is of a type that the implementation chooses ([What the Wording
Guarantees]). That type can't depend on the caller's, and the allocator must
forward to whatever the caller chose, so its `allocate` can't be `noexcept`.
Checking the factory's sender against the erased receiver as it is would
therefore reject a `noexcept` `function` whose factory returns another, as a
decorator that forwards every call to a backing store's `noexcept` interface
does. `noexcept` `function`s wouldn't compose, against requirement 2.

Instead, for a type that doesn't declare the query, the check connects the
factory's sender to a receiver that is the erased receiver in every respect but
one. Its environment's frame allocator
declares its `allocate` `noexcept`, and is never called; it exists only for
the check. The check then answers the question the promise asks, whether
connecting throws for any reason other than a failed frame allocation, and the
outer `connect`'s exception specification accounts for frame allocation.

The substitution is sound as long as a sender's `connect` depends on its frame
allocator's exception behaviour only through calls to `allocate`, because the
check sees the stand-in's type while the sender, at run time, sees the real
one. Adaptors that forward `get_frame_allocator` to their children and compute
their own `connect`'s exception specification from their children's meet that
condition, so a nested `noexcept` `function` is accepted through them. An
adaptor that hides `get_frame_allocator` from its children leaves the inner
`function` to its fallback, which can fail whatever the caller chose, so the
check rejects it. An adaptor that connects a child after the operation starts,
as `let_value` does, reports the child's failure as a completion, which the
type must declare, as [Full Control]'s `cache` does.

Two alternatives were rejected. Trusting a nested `function` as a transformed
sender is trusted would make an exception for one type that a user's own
type-erasing sender couldn't share. Checking against the erased receiver as it
is keeps `noexcept` `function`s from composing.

## What a `noexcept` Type Trusts

What a `noexcept` `function` trusts is narrower than it may look. The domains
that can transform the factory's sender depend only on that sender and on the
erased receiver's environment, which answers only the declared queries and
`get_frame_allocator` ([Required Queries]). The caller's domain reaches the
implementation only through a declared query, such as `get_domain` or
`get_scheduler`, and then only as the type that the query names. A type that
declares `get_domain` with a particular domain admits only callers whose
environments answer with that domain, and the implementation sees the domain
the type names. Which domains can transform the implementation's sender is
therefore fixed when the `function` is constructed, by the implementer's sender
and the author's declared queries, and a caller can't bring a throwing
transformation into play by connecting a `noexcept` `function` in an
unexpected environment. Trusting a
transformation therefore fits the principle in [Who Answers for What]. The
domains belong to the side of the interface that declares and implements it,
not to the caller.

That side chooses them only implicitly, though. Declaring a `get_scheduler_t`
query brings that scheduler's domain in, because `get_domain` falls back to it
([exec.get.domain]{.sref}), and nothing checks what that domain's
transformations do. If one throws where the `function`'s `connect` is
`noexcept` ([The Rule]), the program terminates with no diagnostic to say why.
Elsewhere, the caller gets an exception that the type promised it wouldn't.
The fix is to drop `noexcept`, or the query.

The second of the [Questions for SG1] asks whether the type should have to name
the domains it trusts. That could be checked exactly: the constructor can tell
whether a domain transforms the factory's sender, and could reject a `noexcept`
`function` whose sender is transformed unless its type names the transforming
domain. This paper doesn't propose that, for three reasons, the first weighing
most:

1. **Naming a domain verifies nothing.** When a trusted domain throws, the
   author's fix is the same whether or not the type named it.
2. **It depends on questions that aren't settled.** How a `function` should
   report its completion domain, and whether a domain may transform an opaque
   sender from outside, are open ([Domains and Type Erasure]), and `attrs`
   already gives a domain named in the type a different meaning ([Required
   Queries]).
3. **It adds interface for a narrow hazard.**

It would also raise a question of its own. The author fixes the queries, but
the implementer chooses the sender, and with it the sender's completion domain,
so it isn't clear whose declaration the check should consult.

## Reporting Allocation Failure as a Completion

A third policy would report a failed frame allocation as a completion. A
`function` whose completion signatures declared an error such as
`set_error_t(frame_allocation_error)` could catch the failure in `connect` and
report it when started, so its `connect` would be `noexcept` whatever the
caller's allocator, and the interface's author would have opted in by declaring
the error. nvexec has implementation experience with the pattern: its
operation states allocate device memory when constructed, catch the failure,
and report it from `start` as `set_error(cudaError_t)`. This paper doesn't
propose such a channel; [Open Questions and Polls] asks LEWG whether to pursue
one.

An asynchronous frame allocator, whose `allocate` returns a sender, would lead
to the same channel by another route. A `function` couldn't allocate its frame
in `connect` from such an allocator. It would allocate once the operation
starts and connect the implementation's sender when the allocation completes,
as `let_value` connects its continuation, so a failed allocation could only be
a completion. In exchange for an extra asynchronous step in every call, such an
allocator could make a caller wait for a frame rather than fail, as a pool sized
for a bounded number of operations might, and it would suit memory that is
itself allocated asynchronously, such as CUDA's stream-ordered
`cudaMallocAsync`. Its failures would need a declared error, so a `function`
would admit it through the same opt-in. Designing it belongs to the
frame-allocation paper that [Frame Allocation] describes.

# Domains and Type Erasure

[Checking the Promise] described how connecting a sender first passes it to
`transform_sender`, and [What a `noexcept` Type Trusts] showed that the domains
that can transform a `function`'s implementation are fixed when the `function`
is constructed. A `function` is itself a sender, though, so it also meets
domains from outside the boundary. A domain can transform it, and the
algorithms it's passed to ask it where it completes. This section describes
both, and asks SG1 about the first.

## Transforming a `function` from Outside

`transform_sender` works in two stages ([exec.snd.transform]{.sref}). First,
the domain in which the sender completes may transform it. Then the starting
domain, which `get_domain` reads from the receiver's environment, may transform
the result. Both `connect` and `get_completion_signatures` see the transformed
sender ([exec.connect]{.sref}, [exec.getcomplsigs]{.sref}). For a `function`,
the first stage uses the completion domain that the `function` reports
([Required Queries]), and the second uses the caller's domain, whatever the
`function` reports.

A transformation that reaches a `function` can't do what domains transform
senders for. The implementation is compiled separately, and its sender has
already been transformed by the domains that apply to it, so a domain outside
the boundary can't see the algorithms inside to replace them. It can only wrap
the `function`, or replace it with something else, and either way the caller
no longer gets what the type describes:

1. **The completions can differ from the declared ones.**
   `get_completion_signatures` reports the wrapper's, so the exact completion
   signatures of [Completion Signatures] hold only where no domain intervenes.
2. **So can `connect`'s exception specification.** `std::execution::connect`
   is `noexcept` only if the transformation is, so [The Rule] describes
   `connect` only where no domain intervenes.

Nothing prevents this today. `default_domain` leaves a `function` alone,
because a `function` isn't the sender of a standard algorithm, and nvexec's
`stream_domain` does too, because its transformation is constrained to the
algorithms it knows. Both domains behave well by convention, and nothing
requires others to follow it; a domain whose `transform_sender` accepts any
sender wraps every `function` it meets. The working draft constrains a
domain's replacement for a standard algorithm's sender, which may add only
error and stopped completions ([exec.snd.general]{.sref}), but it says nothing
about a sender that no standard algorithm produced.

The direction this paper suggests is an opt-out that a sender declares in its
attributes and `transform_sender` checks once. Both stages would return a
sender that opts out unchanged, whatever the domains, and because `connect` and
`get_completion_signatures` both go through `transform_sender`, the one check
covers both. A domain would keep one power over such a sender. It could reject
it, making connecting it ill-formed, as a domain whose resource can't run code
it can't see would need to. A rejection tells the caller at compile time what a
wrapper would hide. The boundary would then be domain-neutral in both
directions. The caller's domain already reaches the implementation only through
a declared query ([Required Queries]), and it would no longer act on the
`function` from outside either. `function` would opt out, and so could any type-erasing
sender a user writes. `task` is a natural candidate too, since a coroutine's
body is equally out of a domain's reach, and a separate paper could take it up.

Two alternatives were rejected:

1. **A rule in `connect` that skips the transformation for `function`.** It
   would miss `get_completion_signatures`, which transforms too, and it would
   make an exception for one type that a user's own type-erasing sender
   couldn't share.
2. **Reporting a completion domain whose transformation does nothing.** The
   second stage uses the caller's domain whatever the sender reports, so this
   couldn't stop the caller's domain at all. A domain invented to opt out
   would also spoil comparisons between domains, such as the common domain of
   `when_all`'s children (*`COMMON-DOMAIN`*, [exec.snd.expos]{.sref}).

The first of the [Questions for SG1] asks whether this is worth solving,
whether an opt-out is the right direction, and whether it belongs in this paper
or its own. This paper proposes no wording for it.

## Where a `function` Starts and Completes

A receiver's environment tells a sender, through `get_domain`, the domain in
which its operation is started ([exec.get.domain]{.sref}), and a sender that
completes inline, such as `just()`, reports that domain as the one it completes
in. A `function`'s implementation sees the erased receiver's environment,
which doesn't forward `get_domain` unless the type declares it ([Required
Queries]), so `get_domain` falls back to `default_domain` there. A caller
started anywhere else therefore tells the implementation that it was started
somewhere it wasn't. Every caller on `parallel_scheduler` is such a caller,
because that scheduler has its own domain ([exec.par.scheduler]{.sref}).

Whether that matters depends on where the implementation completes. This
caller looks up a document and checksums its blocks in parallel:

```{.cpp file="fn/checksum_blocks.cpp" caption="checksum_blocks.cpp"}
#include "kv_store.hpp"

#include <cstddef>
#include <cstdint>
#include <optional>
#include <span>
#include <string>
#include <string_view>
#include <utility>

// the checksum of doc's i'th block
std::uint32_t block_checksum(std::string_view doc, std::size_t i);

// looks up key and checksums each block of the document in parallel
void checksum_blocks(kv_store const& store, std::string key,
                     std::span<std::uint32_t> sums) {
  ex::sync_wait(ex::starts_on(
      // the caller's environment says the work starts in this scheduler's
      // domain
      ex::get_parallel_scheduler(),
      // the erased receiver says default_domain; a cache completes a hit
      // inline, on a parallel_scheduler thread, and a miss on remote_store's
      // timer thread, and reports default_domain either way
      store.get(std::move(key))
          // bulk is customized for its predecessor's completion domain, so
          // default_domain's bulk runs, serially, even after a hit
          | ex::bulk(ex::par, sums.size(),
                     [sums](std::size_t i,
                            std::optional<std::string> const& doc) {
                       sums[i] = doc ? block_checksum(*doc, i) : 0;
                     })));
}
```

`parallel_scheduler`'s domain customizes `bulk` only through the first stage
of `transform_sender`, the one that uses the completion domain of the sender
being transformed ([exec.snd.transform]{.sref}), and a `bulk` completes where
its predecessor does. In stdexec, `just() | bulk(…)` started on
`parallel_scheduler` runs on several threads, while `cache` followed by the
same `bulk` runs on one, after a hit as after a miss. After a miss, that is
right: `remote_store` completes on its timer's thread, which is in
`default_domain`. After a hit it is wrong, and not only slow. `cache` completes
on a `parallel_scheduler` thread while reporting `default_domain`, and a
reported completion domain is a promise; if a completion happens on an execution
agent of a resource in another domain, the behaviour is undefined
([exec.get.compl.domain]{.sref}). An implementation can ignore the start
domain it's told only if it never completes on the agent that started it.

Neither of the places that check a `function` can tell a hit from a miss. The
constructor checks the factory's sender against the erased receiver, where a
sender that completes inline looks as if it completes in `default_domain`.
`connect` sees the caller's start domain, but by then the implementation's
type has been erased. Each answer below therefore treats every implementation
of `get` alike:

+--------------------------------------+--------------------------------------+--------------------------------------+
| What `get` reports                   | Started on `parallel_scheduler`,     | Started on `parallel_scheduler`,     |
|                                      | after a `cache` hit                  | after a miss or from `remote_store`  |
+:=====================================+:=====================================+:=====================================+
| `default_domain`, as stdexec does    | serial `bulk`; the report is false   | serial `bulk`, correctly             |
| today                                |                                      |                                      |
+--------------------------------------+--------------------------------------+--------------------------------------+
| No completion domain                 | as above                             | as above                             |
+--------------------------------------+--------------------------------------+--------------------------------------+
| *`COMMON-DOMAIN`* of the start       | ill-formed                           | ill-formed                           |
| domain and the declared one          |                                      |                                      |
+--------------------------------------+--------------------------------------+--------------------------------------+
| Callers whose start domain differs   | ill-formed                           | ill-formed                           |
| are rejected at `connect`            |                                      |                                      |
+--------------------------------------+--------------------------------------+--------------------------------------+

Making no claim changes nothing for `bulk`, because a sender that reports no
completion domain is transformed as if it completed in `default_domain`
([exec.snd.transform]{.sref}). It also leaves an algorithm that combines
children to guess. `when_all` reports the common domain of the agents on which
its completions can happen ([exec.snd.general]{.sref}) and completes from
within whichever child completes last ([exec.when.all]{.sref}), but a child's
type says where its completions happen only through its attributes. The
exposition-only *`COMPL-DOMAIN`* ([exec.snd.expos]{.sref}), which nothing in
the working draft yet uses, would guess that a child making no claim completes
where its siblings do.

The other two answers keep every report true, at the price of rejecting the
example. Because the implementation sees nothing of the caller beyond the
declared queries, it completes either where its own sender says or where it
was started, so a `function` could report the common domain of the two,
*`COMMON-DOMAIN`*`(get_domain(env), D)` ([exec.snd.expos]{.sref}), where `D`
is the domain its type declares. That is exact for every caller in `D`. On
`parallel_scheduler` it is an `indeterminate_domain` naming both, whose
`transform_sender` requires the domains to agree
([exec.domain.indeterminate]{.sref}), and the two customize `bulk`
differently, so the example becomes ill-formed. Rejecting at `connect` every
caller whose start domain differs from the erased receiver's is simpler and
stricter, since it rejects even a caller with no `bulk` to customize, and a type
that avoids it by declaring `get_domain` admits callers in only that domain
([What a `noexcept` Type Trusts]). A type could instead declare that its operation
never completes on the agent that starts it, which the constructor could check
by asking the factory's sender for its completion domain under a second start
domain, but `kv_store::get` couldn't declare that, because `cache` completes
hits inline. This paper proposes none of these, and leaves the question open.

# Future Directions

Earlier sections leave several questions to later papers: the rest of a
frame-allocation design ([Left to a Later Paper]), a typed channel for
frame-allocation failure ([Reporting Allocation Failure as a Completion]), a
way for opaque senders to opt out of transformation from outside ([Transforming
a `function` from Outside]), and the completion domain a `function` should
report ([Where a `function` Starts and Completes]). This section describes one
more, a shorter way to declare common interfaces, which this paper deliberately
doesn't propose.

## A Convenience Form

Every interface in this paper is declared through `async_fn`, because the
proposed form of `function` spells out its completion signatures. R0 also
proposed a shorter form, whose first template argument is an ordinary function
type and whose completion signatures are computed from that type. The
reference implementation still provides it as an extension, so `kv_store` could
be declared like this:

```{.cpp file="future/kv_store.hpp" caption="kv_store.hpp (not proposed)"}
#include <exec/function.hpp>

#include <optional>
#include <string>

struct kv_store {
  virtual ~kv_store() = default;
  virtual exec::function<std::optional<std::string>(std::string) const &>
  get(std::string key) const = 0;
};
```

The reference implementation computes the completions as R0 specified them. A
return type `R` gives `set_value_t(R)`, or `set_value_t()` if `R` is `void`.
Every such type gets `set_stopped_t()`, and one that isn't `noexcept` also gets
`set_error_t(exception_ptr)`. `get`'s return type is therefore not just
equivalent to `async_fn<std::optional<std::string>(std::string) const &>`, but
the same type. Since the order of completion signatures doesn't matter
([Completion Signatures]), any alias that spells out the same completions names
that type too. An interface declared through one codebase's alias can be
overridden through another's, or through a standard form adopted later.

This paper proposes only the form whose return type is `sender_tag`, for two
reasons:

1. **The defaults couldn't be changed.** Once standardized, the computed
   completions would be part of the type of every interface declared with
   them, so changing a default would change those interfaces' types, and with
   them every caller's ABI. This paper's `function` accepts no return type but
   `sender_tag` ([The Call]), so a later paper can give other return types a
   meaning without changing the meaning of any valid program.
2. **The defaults aren't obvious.** Each one makes a choice that the proposed
   form leaves to the interface's author, and as the questions below show, the
   arguments for each choice pull in different directions.

Until a later paper settles them, code that wants a short spelling can write
an alias, as this paper does, and aliases that agree on the completions
interoperate.

::: ednote
**Expand:** Show the convenience form with `queries` and `attrs`, as R0 did,
and list what it can't express: more than one value completion, a value
completion with more than one argument, and errors other than `exception_ptr`,
so neither [Full Control]'s `kv_store` nor a `function` wrapping nvexec's
`cudaError_t` channel.
:::

A follow-up paper would have to answer at least three questions:

1. **Should the stop token be forwarded by default?** Today it isn't, in either
   form. A caller that gives up on a cache miss, as `when_all` does when a
   sibling fails, requests a stop that never reaches `remote_store`, so the
   `when_all` completes only once `remote_store`'s timer fires. The result is
   correct, only late, so nothing tells the interface's author that every
   caller has lost cancellation. Cancellation runs through `std::execution`,
   and someone declaring an interface in the short form would reasonably
   expect it to be cancellable like any other sender. Against that, a forwarded
   query is a dependence ([Required Queries]). If the default declared an
   `inplace_stop_token`, every caller would have to provide one, so a caller
   with another kind of stop token, or with none, such as `sync_wait`,
   couldn't connect a `function` declared in the short form. A default would
   also make the third template
   argument ambiguous. If an explicit `queries` replaced the default,
   `queries<>` would mean no stop token but still not mean no queries, since
   the frame allocator is always provided; if it added to the default, an
   interface couldn't opt out.
2. **Should every computed form complete stopped?** At R0's presentation in
   Brno, the question came up whether `noexcept`, which removes the error
   completion, should remove the stopped completion too. A stopped completion
   isn't an exception, so `noexcept` is the wrong spelling for it, but the
   question stands. An implementation can complete stopped without a forwarded
   stop token, for example when a sender it runs completes stopped, or when it
   uses `associate` with a scope that has closed, so the answer to the first question doesn't
   settle this one. The costs differ, too. Forwarding a stop token costs every
   operation at run time, while a declared stopped completion costs nothing at
   run time, but every caller's types must allow for it.
3. **Should `noexcept` remove the exception?** In the proposed form, `noexcept`
   promises that connecting the `function` doesn't throw ([The Exception
   Contract of `connect`]), and the completion signatures say separately
   whether the operation can complete with an exception. The convenience form
   has only the function type, so in R0 and the reference implementation,
   `noexcept` says both. That follows the synchronous analogy, in which the
   body of a `noexcept` function can't throw either, but it leaves no short
   spelling for an interface whose `connect` can't throw but whose operation can
   still fail with an exception, or the reverse. Under this paper's meaning of
   `noexcept`, removing the exception would be a convention of the convenience
   form, not a consequence of `noexcept`.

[Questions for SG1] asks whether these questions are worth a follow-up paper.

::: ednote
**Expand:** Make each question concrete with the running example: for the
first, a compiled example of a caller that times out a miss to `remote_store`;
for the third, the two combinations the short form can't spell. Name the
principles the answers trade against each other: good defaults, paying only for
what is used, the convenience form being the one most code would use, and the
difference between utilities that are convenient and those that are minimal.
:::

::: ednote
**Expand:** Add a subsection on coroutines that return a `function`. Calling
such a coroutine would only store its arguments, and `connect` would allocate
its frame from the caller's frame allocator, so [Factories]' coroutine `cache`
would allocate only as the sender-expression version does, and the frame would
be allocated after the allocator is known ([Frame Allocators for Coroutines]).
Not proposed; leave heap-allocation elision out. Update the opening's count.
:::

::: ednote
**Expand:** Add a subsection on conversions between specializations, none of
which this paper proposes. Converting to a type that isn't `noexcept`, to a
superset of completion signatures, or to a superset of queries is sound, as
converting a pointer to a `noexcept` function to a plain one is. Converting to
fewer queries isn't, because the implementation was checked against an
environment that answers them. Converting `derived&` to `base&` adapts values
rather than widening the type, and doesn't help overrides, which must return
the base's type. Say that conversions can be added later, since today no
specialization converts to another, and that a widening conversion might reuse
the source's representation rather than nest a second frame. Update the
opening's count.
:::

::: ednote
**Expand:** If there is room after the coroutine subsection, add a short one on
immovable curried arguments: a declaration form that curries a type's
constructor arguments and constructs the object in the frame at `connect`,
passing the factory a reference, as an immovable by-value parameter is
materialized in a callee's frame. Declaration only, not proposed; cite
[@P4337R0] for in-frame construction. Update the opening's count.
:::

## `std::execution::get_frame_allocator`

Add a new subsection to the end of [exec.queries]{.sref} named
[exec.get.frame.allocator]:

:::add

[33.5.?]{.pnum} **`execution::get_frame_allocator`**

[1]{.pnum} `get_frame_allocator` asks a queryable object for its associated
frame allocator.

[2]{.pnum} The name `get_frame_allocator` denotes a query object. For a
subexpression `env`, `get_frame_allocator(env)` is expression-equivalent to
`$MANDATE-NOTHROW$($AS-CONST$(env).query(get_frame_allocator))`

*Mandates*: If the expression above is well-formed, its type satisfies
`$simple-allocator$` ([allocator.requirements.general]{.sref}).

[3]{.pnum} `forwarding_query(get_frame_allocator)` is a core constant
expression and has value `true`.

:::
