# Abstract

[@P4223R1] proposes `std::execution::function`, a type that lets an interface
declare an asynchronous operation the way a function declaration declares a
synchronous one. Implementing such an interface today means writing a sender
expression or a hand-written sender, and [@P4223R1] concedes that a `task`
coroutine expresses the same logic more simply. This paper proposes that a
function whose return type is a specialization of `function` may have a
coroutine body. The compiler generates the sender that the body describes. No
promise type, coroutine handle or call-time frame allocation is involved: the
body's frame is allocated when the returned `function` is connected, through
the receiver's frame allocator, exactly as for any other `function`.

# Introduction

A sender's operation state is an asynchronous stack frame. Every sender
algorithm in [@P2300R10] manages one by hand: it decides which child operation
states are live in which phase, constructs and destroys them in place, stores
results that must outlive a completion, and arranges for the right thing to
happen when a child completes before its `start` returns. Coroutines give the
same structure to the compiler for synchronous-looking code, but C++20
coroutines do it through a promise type and a heap-allocated frame whose
allocation is fixed when the coroutine is called.

`function` [@P4223R1] already decides where an asynchronous frame comes from.
Its operation state is allocated at `connect`, through the frame allocator in
the receiver's environment, and its lifetime nests like a stack frame's along
each sequential path. What it doesn't provide is a convenient way to write the
body. This paper closes that gap by letting the compiler generate the sender
behind a `function`, from an ordinary coroutine body.

::: draftnote
Pre-empt here: "isn't this just `task`?" Short answer for the sketch: `task`
fixes its frame allocation at the call, can't avoid `exception_ptr` for
errors, and has `task`'s scheduler affinity; the proposal keeps `function`'s
allocation model and completion signatures. Say when `task` matches it.
:::

# Motivation

The running example of [@P4223R1] is a caching decorator over a key-value
store. With a sender expression, the hit and miss paths return different sender
types, so the implementation needs a sum-type sender such as [@P4329R0]'s
`variant_sender`:

```cpp
// From P4223R1's final example (schematic; copy the real one).
function<sender_tag(std::string) const &, /* completions */>
cache::get(std::string key) const {
  return {*this, std::move(key), [](cache const& self, std::string&& key) {
    using result = variant_sender</* hit sender */, /* miss sender */>;
    if (auto hit = self.lookup_(key))
      return result(just(std::move(*hit)));
    return result(self.backing_->get(std::move(key)));
  }};
}
```

As a `task` coroutine, the same logic is three lines, but the declaration
changes type and the frame is allocated at the call. With this proposal, the
declaration is unchanged and the definition is the three lines:

```cpp
function<sender_tag(std::string) const &, /* completions */>
cache::get(std::string key) const {
  if (auto hit = lookup_(key))
    co_return hit;
  co_return co_await backing_->get(std::move(key));
}
```

Callers can't tell which way `cache::get` is defined. The branch is ordinary
control flow, so no sum-type sender is needed, and the hit path completes inline
without connecting a child.

::: draftnote
Add a second motivating example where hand-written frame management is the
pain point: a loop that reads until a buffer is full, compared with a
hand-written `repeat`-style operation state.
:::

# Design Overview

## Which functions are asynchronous functions

A function is an *asynchronous function* if its declared return type is a
specialization of `function` and its body contains `co_await` or `co_return`.
Nothing in the declaration distinguishes it, and calling it works exactly as
calling any other function that returns that `function` type. There is no
promise type and no customization through `coroutine_traits`: the semantics are
fixed by the language and by `function`'s type.

The curried parameters are exactly the function's parameters, plus the implicit
object as the call type's qualifiers specify. A definition whose `function` type
disagrees with its parameters is ill-formed.

## The as-if rewrite

An asynchronous function's definition is equivalent to one that returns a
`function` constructed from its parameters and a factory returning a
compiler-generated sender:

```cpp
function<sender_tag(int) noexcept,
         completion_signatures<set_value_t(int), set_error_t(error_code)>>
foo(int i) noexcept {
  co_return i * co_await some_int();
}

// is equivalent to (same declaration)
{
  return function<…>{i, [](int i) noexcept { return __generated_sender(i); }};
}

struct __generated_sender {           // unnamed, like a closure type
  int __i_;
  __erased_opstate connect(rcvr_t);   // rcvr_t, __erased_opstate: function's
};                                    // erased receiver and operation state
```

- The generated sender holds only the parameters. Its `connect` connects no
  children: the body runs from `start`, and each child is connected when the
  body reaches its `co_await`.
- `rcvr_t` and `__erased_opstate` are `function`'s exposition-only erased
  receiver and erased operation state. Their sizes depend only on `function`'s
  type, never on the body.
- The body's frame is not a C++ type. It lives in the erased operation state's
  inline buffer or in storage from the frame allocator, and its layout is the
  implementation's choice (see [Layout and Implementation Strategy]).

## Not C++20 coroutines

No `coroutine_handle` exists, and nothing is allocated when the function is
called. The two designs share keywords and the shape of the generated code, but
an asynchronous function's frame is an operation state: it is created by
`connect`, started by `start`, and destroyed by its owner after it completes.
That last property simplifies the generated code (see [Completion]).

# Semantics

::: draftnote
Each subsection should open with an example and its translation into generated
code. Most of these rules need a worked example before EWG will believe them.
:::

## Parameters and locals

Parameters and locals live in the frame and are never moved after they are
constructed, so their addresses are stable across suspension:

```cpp
std::string const& k = key;
auto value = co_await backing_->get(k);   // the child borrows k across the suspension
```

A library rewrite that moved locals into continuations (`let_value`-style)
would break this, so the semantics are specified as a generated state machine,
with the standard algorithms as intuition only.

## `co_await`

- `co_await s` connects `s` to a receiver generated for this suspension point,
  in storage the frame already owns, and starts it. The body continues when the
  operation completes with a value.
- A body has at most one outstanding `co_await`, however its operands are
  sequenced. Function arguments containing `co_await` are awaited one after the
  other in an unspecified order; unsequenced operands (`co_await a + co_await
  b`) don't overlap either, since starting both would introduce races between
  the senders' own work. Concurrency is explicit (`co_await when_all(a, b)`).
- The awaited operation lives to the end of the full-expression, as a C++20
  awaiter does. So does the awaited sender temporary. The result is stored in
  the frame, so a reference result that refers into the child stays valid for
  the rest of the full-expression.
- The usual hazard follows: `auto&& r = co_await s;` dangles when the result
  refers into the child.
- In v1, `co_await` of a sender with more than one value completion signature is
  ill-formed (see [Future Directions]).

## Iteration and stack depth

A loop containing `co_await` reuses the same storage on every iteration; it
doesn't grow the frame. Without care, though, it grows the stack: when a child
completes inside its own `start`, resuming the body from that completion nests
each iteration one level deeper. [@P3801R0] reports this for `task`.

Proposed rule:

> If the operation started by a `co_await` completes on the thread that called
> its `start`, before that call returns, then the remainder of the coroutine
> body is evaluated after the call to `start` returns.

The rule mentions no stack, but it is observable (a child's `start` that does
something after calling `set_value` sees that happen before the body continues)
and it bounds stack depth.

- Implementations need a private per-thread slot to tell whether a completion is
  nested inside the corresponding `start`. The fact has to cross the child's
  `start` and whatever calls the generated receiver, so it can't be passed as a
  parameter, and it can't live in the frame, which may already be destroyed by
  another thread when `start` returns. Precedent for private per-thread
  runtime state: the exception-handling runtime.
- The compiler can omit the check when a child's completion behaviour is known
  statically.
- Rejected: an atomic handshake in the frame (whichever side loses the race
  continues the body, so a child that completes on another thread could have the
  body continue on the starting thread, breaking `co_await continues_on(s,
  sch)`); resuming unconditionally; a trampoline scheduler.

::: draftnote
Open: GPU device code has no `thread_local`; ask implementers whether a
per-thread slot is feasible there. Name the deadlock risk: a child whose `start`
calls `set_value` and then waits for something the continuation provides.
Check P3206's status before relying on a completion-behaviour query.
:::

## Completion

`co_return e` completes with `set_value` of `e`'s value; falling off the end of
the body completes with `set_value()`. Before any completion, every live local
and temporary is destroyed, and the completion is the frame's last action.

- `co_return`'s operand is materialized on the stack of the code that completes,
  since nothing suspends after it.
- A completion forwarded from a child has its arguments decay-copied first,
  because they may refer into the child.
- The precedent is C++20: a coroutine's locals are destroyed before
  `final_suspend` resumes the continuation. It matters for code such as a
  `std::lock_guard` local, which must not still be held when the receiver's
  continuation runs.

Because a started operation can't be destroyed before it completes, and every
completion first destroys what is live, the frame's destructor has nothing of
the body's to clean up except the parameters. Contrast C++20, where a suspended
coroutine can be destroyed through its handle at any suspension point.

`co_return co_await s` may forward `s`'s completions directly, passing
references through and destroying the child afterwards, when nothing else with a
non-trivial destructor is live at that point.

::: draftnote
Open: a conversion rule for `co_return` when several value signatures are
declared (candidate: overload resolution among them).
:::

## Errors and stopped

The question is what an awaited sender's non-value completions do to the body.

- **`set_error(exception_ptr)`** enters the body as the exception it holds, so
  `try`/`catch` around a `co_await` catches it as it would in `task`. Without an
  enclosing handler, it completes the body with `set_error(exception_ptr)`
  directly; nothing is rethrown.
- **`set_error(E)` for other `E`** enters the innermost enclosing handler that
  would catch a thrown `E`, without a throw. The choice is static: a thrown
  object's type is the static type of the `throw` operand, and `E` is known from
  the child's completion signatures. If no handler matches, the body completes
  with `set_error(E)`.
- **`set_stopped`** is not an error. No handler catches it, including
  `catch (...)`; it completes the body with `set_stopped()`.

```cpp
function<sender_tag(int) noexcept,
         completion_signatures<set_error_t(error_code), set_value_t()>> coro(int);

function<sender_tag(int) noexcept, completion_signatures<set_value_t()>>
caller(int i) {
  try {
    co_await coro(i);
  } catch (error_code ec) {   // entered by coro's set_error(error_code); nothing is thrown
    std::print("Encountered an error: {}\n", ec.message());
  }
}
```

So one rule covers both: an error leaving the body completes it with
`set_error` of that error, where a thrown exception's error is its
`exception_ptr`.

- The stored error plays the role of the exception object. It is stored by value
  before the child is destroyed, and a handler's parameter binds to it as it
  would to an exception object.
- A `try` block spanning a suspension point has its handlers shared by every
  segment of the body it covers, as in C++20 coroutine lowering.
- Rejected: rethrowing every error, as `task`'s sender awaitable does (it turns
  `error_code` into exceptions and needs exception support); forwarding every
  error (then `catch (...)` wouldn't catch an awaited `exception_ptr`).

::: draftnote
Open, ranked by design work:

1. `throw;` and `std::current_exception()` in a handler entered by a
   completion, where no exception object exists. A handler reachable both ways
   needs a flag; `throw;` could mean "propagate this completion", and
   `current_exception()` could return `make_exception_ptr(e)` or null.
2. `-fno-exceptions` and device code: compilers reject `try` without
   exceptions, but this is the code that most wants non-exception errors.
3. `co_await` in a handler stays ill-formed, as in C++20, though C++20's
   reason (the per-thread currently-handled exception) doesn't apply to
   handlers only completions can reach.

Check the `as_awaitable` precedent against the working draft before citing it.
:::

## Checking completions

- Every completion the body can produce must be among the declared ones: the
  forwarded completions of every awaited child (decayed), the errors no handler
  catches, `set_value` from each `co_return`, and `set_error(exception_ptr)`
  where an exception can escape.
- Where the body is potentially-throwing and `set_error(exception_ptr)` isn't
  declared, an escaping exception terminates, as it does from a `noexcept`
  function. C++ knows only *potentially* throwing, so this can't be made
  ill-formed.

# Layout and Implementation Strategy

Nothing outside the generated code needs the size of the body's frame.

- Callers see only `function`.
- The body can't name the generated sender.
- Static checks work on types: completion signatures and `noexcept` analysis
  never need the frame's size.
- `function`'s erased operation state is exposition-only, so the library and
  compiler can co-design it to hold either a library operation state or a
  compiler-generated frame. The coupling is private, through builtins, as with
  `std::source_location` and `coroutine_handle`.

So the standard specifies behaviour and leaves layout to the implementation:

- **Front-end layout** sizes the frame conservatively: storage overlaps across
  statements, and a full-expression's temporaries are summed.
- **Middle-end layout** sizes it after optimization, from real liveness, as
  Clang and LLVM lay out C++20 coroutine frames.

An implementation could use front-end layout in device code and middle-end
layout elsewhere. This sidesteps the objection [@P1492R0] raised against Core
Coroutines [@P1063R0], which exposed the frame as a type and so needed its
`sizeof` during semantic analysis.

Two co-design points:

- **`function` mustn't erase twice.** It uses the `__erased_opstate` from the
  generated `connect` directly rather than wrapping it.
- **`connect(rcvr_t)` is potentially-throwing.** The frame is acquired through
  `rcvr_t`'s erased frame allocator, whose `allocate` can't be `noexcept`;
  `function`'s own `connect` keeps the conditional `noexcept` [@P4223R1]
  specifies. `function`'s construction-time check knows the generated `connect`
  can throw only when allocating and when moving the parameters, so it treats
  the generated sender as it treats a nested `function`.

## Domains

The generated sender is an ordinary sender, so domains can transform it. A
wrapper can connect it to the wrapper's own receiver, which converts to
`rcvr_t` because a type-erasing receiver must accept any compatible receiver,
and store the resulting `__erased_opstate`. A domain can also replace it, though
a replacement can't reproduce a body it can't see. Domains that dispatch on
known algorithm tags leave it alone.

::: draftnote
Check against P4223R1's wording: whether `rcvr_t`'s converting constructor is
implicit, and whether the erased receiver refers to or owns the receiver.
:::

# Future Directions

- **Handling stopped, and decomposing completions generally.** [@P2688R6]'s
  `match` could decompose a completion set modelled as a closed alternative type
  (one state per signature, with named selectors such as `{ .error:
  std::error_code ec }` and `{ .stopped }`), with exhaustiveness checked. Its
  handlers are ordinary statements, so `co_await` works in them. v1 keeps that
  open by making `catch` never see stopped and multi-value `co_await`
  ill-formed.
- **Spellings for completing with an error or stopped** (`co_return
  with_error(e)` in [@P4282R2]; `co_throw`, `co_stop`). `catch`-as-`set_error`
  doesn't need them, since unmatched errors propagate; exhaustive matching
  would.
- **Compiler-computed completions**, behaving like a deduced return type (the
  definition is needed before use), as an opt-in.
- **`sender_tag(...)`** as shorthand for the function's own parameters.
- **Scheduler affinity**, which `task` has and this proposal doesn't.
- **Sender-level tail calls** (D4438R0, in preparation), which might subsume
  the stack-depth rule.
